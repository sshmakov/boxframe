# Суть проблемы

При перетаскивании группы элементов (мульти-выделение) внутрь box блоки
визуально наезжали на box, но **не становились его дочерними**:
`_commitGroupMove` в `editor.js` отправлял batch-обновление только с
`{id, x, y}` — без определения drop-контейнера и без `parent_id`.
В отличие от одиночного блока (`_commitBlockMove`) и drop из палитры
(`onCanvasDrop`), групповой drag не имел re-parenting.

Помимо этого найден латентный баг расчёта дельты: группа сдвигалась на
`gx - orig.x`, где `gx` — абсолютная позиция блока, а `orig.x` —
сохранённая при старте drag координата (относительная, если блок внутри
box). Если таскаемый блок сам находился в контейнере, группа уезжала не
на дельту мыши, а на дельту + смещение контейнера.

# Задача

Сделать групповой drag согласованным с одиночным:

1. При перетаскивании группы внутрь box все блоки группы, чей центр
   после перемещения попадает в box, становятся его дочерними
   (относительные координаты).
2. При перетаскивании группы из box обратно на канвас блоки
   de-parent'ятся (`parent_id: null`, абсолютные координаты).
3. Починить расчёт дельты группового drag: сдвиг должен быть равен
   дельте мыши независимо от того, в каких контейнерах находились
   блоки до drag.
4. Всё — одним batch-обновлением (один шаг undo/redo).

# Исследование

1. **Одиночный блок и drop из палитры уже умеют re-parenting.**
   `_commitBlockMove` и `onCanvasDrop` используют `_findDropContainer`
   (внутренний box, чья абсолютная область содержит центр блока) +
   `_absToRel`. Групповой drag — единственный путь, где этого не было.
2. **Инфраструктура готова.** Batch PUT `/api/layouts/{id}/blocks`
   принимает `parent_id` в обновлениях, `batchBlocks` в обоих сторах
   (FetchStore/LocalStorageStore) тоже — пробел был только в `editor.js`.
3. **Undo корректен без изменений.** `withHistory` снимает снапшот
   всего состояния перед `batchBlocks` — один batch = один шаг.
4. **Per-block vs per-group определение контейнера.** Сначала
   реализовано по центру всей группы — но блок, оставшийся визуально
   внутри box, был бы ошибочно вырван из него (и наоборот). Правильно —
   то же правило, что для одиночного блока: центр каждого блока
   оценивается отдельно.
5. **Циклы.** Box из самой группы нельзя сбрасывать в себя или в своих
   потомков — при поиске контейнера исключаются поддерева всех
   выбранных блоков (`_subtreeIds` union).
6. **Вложенные структуры.** Блок, чей родитель тоже в группе, не
   обновляется: родитель «несёт» его, относительный оффсет не меняется.
   Вложенные деревья переезжают целиком.
7. **E2E: выбор вложенных блоков.** Marquee-выделение не может стартовать
   на блоке внутри box (курсор попадает на box), поэтому в тестах
   «из box наружу» и «дельта с вложенным» используется click +
   Shift+click. Панель свойств, открывающаяся справа от первого
   клика, может перекрывать другой блок — сначала кликают правый.

# Выполнение задачи

Изменено 2 файла.

**`boxframe/static/js/editor.js`**:
- состояние: `dragGroupAnchor` — абсолютный rect drag-блока на момент
  старта группового drag (сбрасывается в `_resetDrag`);
- `_onMouseMove`: дельта группы = `gx - dragGroupAnchor.x` (абсолютно),
  clamp `-minX/-minY` считается по абсолютным rect всех выбранных
  блоков (`_absoluteRect`), а не по сохранённым (возможно
  относительным) координатам;
- `_isInSubtree(block, ancestorId)` — хелпер: true, если блок —
  потомок данного (ход по цепочке `parent_id`);
- `_commitGroupMove`: для каждого блока группы — новый абсолютный
  rect после сдвига → `_findDropContainer` по его центру (с
  исключением поддерев группы) → в batch-обновление:
  - контейнер найден и блок не в его поддереве →
    `parent_id: container.id` + `_absToRel`;
  - контейнера нет, а блок был в контейнере →
    `parent_id: null` + абсолютные координаты;
  - иначе (тот же родитель) → чистый сдвиг `x + dx, y + dy`;
  - родитель в группе → блок в обновлении не участвует.

**`tests/e2e/test_editor.py`** (3 новых теста, секция
«Group drag ↔ container (re-parenting)»):
- `test_group_drag_into_box_reparents`: box C 24×12 + два блока
  справа; marquee, drag влево → оба блока children C, относительные
  координаты и жёсткий оффсет сохранены;
- `test_group_drag_out_of_box_unparents`: два блока внутри C;
  click + Shift+click, drag вправо → оба `parent_id: null`,

- `test_group_move_with_nested_block_keeps_delta`: регрессия на баг
  дельты — группа «блок из box + корневой блок» сдвигается ровно на
  дельту мыши, вложенный блок остаётся в box.

# Замечания

1. **Критерий re-parenting — центр блока.** Тот же, что у одиночного
   блока: блок «входит» в box, если его центр после перемещения внутри
   box. Для группы это может дать «разрыв» — часть группы внутри box,
   часть снаружи. Это осознанное поведение (последовательность
   одиночных drag дала бы то же). Кандидат на будущую задачу:
   whole-group-критерий (все или ничего) или визуальный preview
   контейнера при drag.
2. **Batch-обновление может быть пустым.** Если вся группа уже внутри
   одного box и ни один блок не меняет родителя, в batch уходят только
   чистые сдвиги — это корректно. Если `dx = dy = 0`, коммит
   пропускается (как и раньше).
3. **`_findDropContainer` вызывается per-block** — O(N·M) по блокам и
   box. Для размеров макетов в MVP это незначимо; при росте можно
   кэшировать абсолютные rect box на время drag.
4. **Static-режим покрыт тем же кодом** — `LocalStorageStore.batchBlocks`
   поддерживает `parent_id`, e2e-тесты для static-режима на re-parenting
   группы не добавлялись (web-режим проверяет общий код `editor.js`).
