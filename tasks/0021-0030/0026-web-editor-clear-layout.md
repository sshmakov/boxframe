# Суть проблемы

В статическом редакторе (задача 0025) уже была кнопка очистки всего
макета с подтверждением, но в web-редакторе (режим с бэкендом,
`templates/pages/editor.html`) её не было. Причина — асимметрия
сторов: у `MemoryStore`/`LocalStorageStore` есть метод `clear()`, а у
`FetchStore` (web-режим) его не было, и в API не существовало
endpoint для удаления всех блоков макета разом.

Итог: чтобы «начать заново» в web-режиме, приходилось удалять блоки
по одному (каждое — со своим `confirm`). Для макета из десятков
элементов это непрактично. В задаче 0025 это было осознанно
отложено: «`clear()` намеренно отсутствует у `FetchStore`… если
понадобится в web-режиме, это отдельная задача».

# Задача

- Добавить кнопку очистки макета для режима редактирования с бэкендом
  (web-режим), с дополнительным подтверждением (случайный клик не
  стирает работу).
- Поведение согласовать со статическим редактором: подтверждение через
  `confirm`, сброс выделения и inline-редактора, кнопка видна только
  при наличии блоков.

# Исследование

1. **Слой store уже изолирован (вывод задачи 0025 подтвердился).**
   `editor.js` не знает о fetch и работает через единый async-
   интерфейс store. Метод `clearLayout()` в `editor.js` существовал
   ещё с задачи 0025 и был режим-независимым: он проверял
   `typeof this.store.clear === "function"` перед вызовом. Поэтому для
   web-режима хватило добавить `clear()` в `FetchStore` и кнопку в
   шаблон — логику редактора менять не пришлось.
2. **Дизайн endpoint.** `DELETE /{layout_id}/blocks` (без `block_id`)
   — естественное REST-дополнение к существующим
   `DELETE /{layout_id}/blocks/{block_id}` (один блок) и
   `DELETE /{layout_id}` (весь layout). Путь отличается от
   `.../blocks/{block_id}`, конфликтов маршрутизации нет.
3. **Bulk-удаление одной строкой.** `delete_all_blocks()` использует
   `delete(Block).where(Block.layout_id == layout_id)` — один SQL-
   запрос на все блоки (включая вложенные). SQLite по умолчанию не
   включает FK-проверки (`PRAGMA foreign_keys` off), а удаляются все
   блоки макета разом (и родители, и дети), так что осиротевших
   `parent_id` не остаётся. Альтернатива (ORM-удаление по одному с
   каскадом `children`) была бы медленнее и громоздче.
4. **Семантика: layout сохраняется, размеры не трогаются.** В отличие
   от `clear()` статического стора (сбрасывает `width`/`height` в
   null), web-очистка удаляет только блоки. Размеры — свойство
   самого макета (задача 0024), а не блоков; «очистить макет» — это
   удалить содержимое, а не пересоздать холст. На практике в
   статическом режиме размеры всё равно всегда null, так что
   расхождение не влияет на поведение.
5. **Подтверждение переиспользовано.** `clearLayout()` уже содержал
   `confirm('Clear the entire layout? All blocks will be removed.')` —
   тот же текст и тот же механизм, что в статическом редакторе и в
   `deleteBlock()`. Дополнительное подтверждение получено без новой
   логики.

# Замечания

1. **Главный вывод: store-абстракция окупилась во второй раз.** Как и в
   задаче 0025, добавление нового поведения (очистка в web-режиме)
   не потребовало менять логику редактора — только метод стора и
   кнопку в шаблоне. `clearLayout()` оказался режим-независимым ещё на
   этапе проектирования 0025 (проверка `typeof store.clear ===
   "function"`), что позволило включить web-режим «бесплатно». Это
   подтверждает правильность архитектуры 0018: новые возможности
   добавляются точечно, без каскадных правок.
2. **`clear()` теперь — универсальный метод интерфейса стора.** Все три
   стора (`FetchStore`, `MemoryStore`, `LocalStorageStore`) его
   реализуют. Проверка `typeof ... === "function"` в `clearLayout()`
   осталась как защита от будущих сторов без очистки, но на практике
   все поддерживают.
3. **Семантическое расхождение осознанно.** Web-очистка сохраняет
   размеры макета, статическая — сбрасывает (но в статическом режиме
   они всегда null). Если когда-нибудь захочется единой семантики,
   стоит вынести её в ядро `createLayoutStore` и явно решить, трогать
   ли размеры.
4. **Ответ endpoint информативен.** `{"ok": true, "deleted": N}` даёт
   число удалённых блоков — удобно для отладки и для ассертов в
   тестах. Редактор значение не использует, поэтому это не влияет на
   фронтенд.
5. **Закрыт долг из задачи 0025.** Замечание №3 той задачи
   («`clear()` намеренно отсутствует у `FetchStore`… если понадобится
   в web-режиме, это отдельная задача») реализовано: новый API-роут
   добавлен, кнопка работает в обоих режимах.
6. **Кнопка видна только при наличии блоков** (`x-show="blocks.length
   > 0"`) — нет смысла предлагать очистить пустой макет; при этом
   `clearLayout()` безопасен в любом состоянии, а `delete_all_blocks()`
   на пустом макете корректно возвращает `deleted == 0`.
