# Суть проблемы

Перенос по словам из задачи 0013 строился на `str.split()` без аргумента, который:

- схлопывает последовательности пробелов в один;
- отбрасывает начальные пробелы строки.

В результате намеренное пробельное оформление контента блока терялось при
рендеринге: `Name        Price` (выравнивание столбцов) превращалось в
`Name Price`. Для AI-readable формата это существенно: пробелы в псевдографике —
часть форматирования (отступы, выравнивание), а не только разделитель слов.
Пробелы, введённые пользователем в контент, должны воспроизводиться в рендере.

# Задача

Исправить перенос по словам так, чтобы пробелы внутри строки учитывались как
форматирование:

- последовательности пробелов сохраняются как есть, если строка помещается в
  контентную область;
- если запас пробелов не помещается и происходит перенос — запас отбрасывается
  (иначе он съел бы ширину новой строки и обрезал бы слово);
- начальные пробелы строки (отступ) сохраняются;
- явные `\n` и hard split длинных слов — без изменений;
- Python- и JS-рендереры дают побайтово идентичный вывод (parity).

# Исследование

1. **Логика переноса в двух местах** — `PseudoGraphicRenderer._wrap_text()`
   (Python) и `wrapText()` (JS-порт, `static/js/core/renderer.js`). Просмотр и
   экспорт идут через общий `render()`, точка изменения одна в каждом рендерере.
2. **Причина** — `raw_line.split()` (Python) / `split(/\s+/).filter(...)` (JS):
   любой whitespace — разделитель, последовательности схлопываются,
   начальные/концевые отбрасываются.
3. **Алгоритм** — строка токенизируется на слова и запасы пробелов
   (`re.findall(r"\S+| +", line)` в Python, `match(/\S+| +/g)` в JS). Запас
   пробелов — токен, как и слово:
   - помещается в текущую строку (`len(current) + len(run) <= width`) —
     дописывается как есть;
   - не помещается и строка непустая — перенос, запас отбрасывается;
   - в начале строки (контента ещё нет) — сохраняется (отступ).
   Проверка добавления слова идёт по длине строки с уже учтёнными пробелами,
   поэтому выравнивание сохраняется точно.
4. **Крайние случаи**:
   - запас пробелов длиннее ширины (начальный) — сохраняется, при отрисовке
     клипится сеткой (строка в итоге rstrip'ится);
   - строка из одних пробелов — рендерится пустой строкой (как раньше);
   - табы и прочий whitespace — по-прежнему разделители слов, поведение не
     изменилось;
   - hard split длинного слова — логика не тронута, работает и со строкой,
     оканчивающейся пробелами.
5. **Parity** — регулярные выражения Python и JS (`\S+| +`) совпадают по
   классам символов для практического (ASCII) контента; подтверждено
   побайтовым сравнением в parity-тестах.

# Замечания

1. **Замечание 2 из задачи 0013 закрыто** — «если понадобится сохранение
   отступов — нужен другой алгоритм»: алгоритм теперь на месте.
2. **Хвостовые пробелы** могут оставаться в результате wrap (например
   `"Name        "` перед переносом) — при отрисовке они клипятся `rstrip()`
   строки сетки, не видны и на parity не влияют.
3. **Табы — не форматирование**: по-прежнему разделители слов (как и раньше).
   Если понадобится выравнивание табами, нужно расширить токенизацию
   (`\t+` отдельным токеном) — и в обоих рендерерах.
4. **Отбрасывание непоместившегося запаса** — осознанный выбор: сохранение его
   как отступа новой строки съело бы ширину и обрезало слово. Другая политика
   (например, сжатие запаса до ширины) меняется в одном месте — ветка
   обработки запасов в `_wrap_text()` / `wrapText()`.
