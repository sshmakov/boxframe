# Суть проблемы

Undo/redo-буфер (задача 0027) живёт в памяти вкладки: `withHistory()`
держит `undoStack`/`redoStack` как обычные JS-массивы. При перезагрузке
страницы (случайный refresh, закрытие вкладки, сбой браузера) буфер
теряется, хотя сам макет переживает перезагрузку (static —
localStorage, web — БД на сервере). Пользователь теряет возможность
отменить последние N операций — ровно в тот момент, когда она нужнее
всего (например, обновил страницу и только потом заметил ошибку). В
web-режиме контраст особенно заметен: макет «бессмертен» на сервере,
а история отмены исчезает.

# Задача

Сделать undo/redo-буфер переживающим перезагрузку страницы в обоих
режимах:

- персистентность стеков снапшотов в localStorage (static и web);
- в web-режиме ключ хранилища scoped на layout (несколько layout'ов
  делят один браузер);
- валидация восстановленных стеков против текущего состояния: если
  макет менялся в другом месте (другая вкладка/клиент/API) —
  устаревший буфер сбрасывается;
- ограничение длины буфера 50 снапшотами в обоих режимах (изменение
  требования из 0027 «буфер без лимита» — мотивация: квота
  localStorage ~5 МБ).

# Исследование

1. **Обёртка store-агностична — персистентность бесплатная опция.**
   `withHistory()` не знает о внутреннем store, а стеки — обычные
   JSON-массивы снапшотов `{width, height, blocks}`. Один и тот же
   механизм работает и с local-store (static), и с fetch-store (web) —
   без дублирования.
2. **Отдельный ключ, а не встраивание стеков в layout-состояние.**
   Формат `{width, height, blocks}` — контракт `replaceState`/
   `readSavedState`/экспорта; смешивание с историей его сломало бы.
   Плюс обёртка универсальная — персистентность должна быть
   ортогональной опцией.
3. **Инвариант согласованности.** После каждой операции: layout-ключ =
   текущее состояние, `undoStack` = состояния до текущего,
   `redoStack` = после. Local-store сохраняет layout при каждой
   мутации (включая `replaceState` из undo/redo), обёртка сохраняет
   стеки при тех же мутациях — ключи не расходятся.
4. **Валидация вместо слепого восстановления.** В web-режиме
   источник правды — сервер: между перезагрузками состояние могло
   измениться (другая вкладка, другой пользователь, API). Слепое
   восстановление стеков позволяло бы undo молча затереть внешние
   изменения снапшотом. Решение: персистить текущее состояние вместе
   со стеками; при первом `load()` сравнить загруженное состояние с
   сохранённым (JSON-равенство). Совпало → восстановить; нет →
   сбросить стеки и удалить запись.
5. **JSON-сравнение здесь надёжно.** В web-режиме все ответы API
   используют одну Pydantic-схему `BlockOut` (GET layout, POST/PUT
   block, batch replace) — набор и порядок полей идентичны, поэтому
   равенство `JSON.stringify` — точная проверка «состояние
   изменилось». Ложное «совпало» невозможно (любое изменение поля
   меняет JSON); ложное «не совпало» — лишь потеря буфера, а не
   данных.
6. **Персистить только после успешной мутации.** `_record()` пушит
   снапшот до мутации; сохранение стеков сразу после push при
   ошибке мутации оставило бы сохранённый буфер на запись впереди
   store. `_persist()` вызывается в конце каждого обёрнутого метода
   (после resolve стора) и в undo/redo (после `_applyState`).
7. **Cap 50 — изменение требования.** 0027 обещала «неограниченный
   буфер» (в памяти это было дёшево). С персистентностью буфер
   попадает в квоту localStorage ~5 МБ (общую с layout'ами в
   web-режиме), поэтому лимит нужен. 50 снапшотов × десятки КБ —
   комфортный запас; отбрасываются самые старые. Cap применяется к
   обоим стекам и к перистируемой записи (защита от смены
   `maxSnapshots` между сессиями).
8. **QuotaExceeded — graceful degradation.** `setItem` в try/catch:
   при переполнении квоты или в private mode — warn и продолжение в
   памяти (буфер работает, просто не переживает reload) — тот же
   паттерн, что у персистентности layout в `store.js`.

# Выполнение задачи

Изменено 4 файла (+349/−57), добавлен 1 файл задач.

**`boxframe/static/js/core/history.js`**
- новые опции: `storage` (injectable `{getItem, setItem}`),
  `historyKey` (default `boxframe.static.history`), `maxSnapshots`
  (default 50);
- при создании: чтение записи из storage (битый JSON → пустые стеки,
  без падения), удержание в `_pending`;
- `_settlePending()` — вызывается в первом `load()` (и в ленивом
  `_ensureState`): сохранённое состояние совпало с загруженным →
  восстановить стеки (+ cap, coalescing-состояние
  `_lastKey`/`_lastTime`, `onChange` для UI-счётчиков); не совпало →
  сбросить стеки и удалить запись (`removeItem`, если доступен);
- `_persist()` — запись `{undoStack, redoStack, lastKey, lastTime,
  state}` после каждой успешной мутации, undo, redo; try/catch
  (квота/private mode → warn);
- `_cap(stack)` — обрезка до `maxSnapshots` (старые первые);
  применяется в `_record`, `undo`, `redo` и при восстановлении.

**`boxframe/static/js/editor.js`**

# Замечания

1. **«Неограниченный буфер» стал «50 шагов».** Осознанное изменение
   требования: персистентность унесла буфер в квоту браузера, лимит
   необходим. Если 50 окажется мало — `maxSnapshots` это параметр,
   править код не нужно.
2. **Семантика буфера в web-режиме: «живёт, пока серверное состояние
   не изменилось».** При изменении макета в другом месте буфер молча
   сбрасывается (undo-кнопка становится disabled). Это компромисс
   без серверного версионирования; если понадобится «бессмертная» и
   общая история — серверный undo-лог (0027, «Исследование» №2),
   отдельная задача.
3. **Точка валидации — `load()`.** Редактор всегда грузит макет на
   init (`fetchBlocks`), поэтому буфер восстанавливается до первого
   действия пользователя. Если `load()` так и не вызван, буфер
   остаётся пустым — безопасная деградация.
4. **Две вкладки одного layout — last-write-wins** и для layout
   (static), и для записи истории. Предсуществующее ограничение
   клиентской персистентности, не новое.
5. **Store-абстракция окупилась в четвёртый раз (0025/0026/0027):**
   фича добавлена точечно — опции обёртки + несколько строк в
   редакторе; логика мутаций не тронута, оба режима получили
   персистентность бесплатно.
6. **Операционная заметка про e2e:** на :8000 обычно уже работает
   dev-сервер из этого же чекаута (каталог доступен по двум путям —
   bind mount `/home/...` и `/media/...`), поэтому e2e можно гонять
   против него, а собственный uvicorn на этот порт поднимать не
   нужно (порт занят). Перед e2e стоит проверять, кто держит порт.
