# Суть проблемы

Компонент `button` рендерился как обычный блок: полная рамка по четырём
сторонам при любой высоте ≥ 2, а при `height=1` рамка не рисовалась вовсе
(только контент). Внешний вид кнопки не соответствовал принятой в
псевдографике конвенции: однострочная кнопка читается как `[label]`,
двухстрочная — без верхней рамки, а label должен стоять по центру по
вертикали. Для AI-readable формата форма кнопки — часть семантики: по
высоте/рамке агент должен однозначно определять, что блок — кнопка.

Второй пробел — поведение редактора: дефолтная кнопка создавалась 12×1, но
минимальная высота при resize была 2 (как у всех блоков, кроме линий) —
кнопку высотой 1 нельзя было сохранить перетаскиванием, хотя это
основной случай из спецификации.

# Задача

Сделать поведение и рендер компонента `button` соответствующим примерам:

```text
   Кнопка высотой 1 символ:           [Button        ]

   Кнопка высотой 2 символа:          │Button        │
                                      └──────────────┘

                                      ┌──────────────┐
   Кнопка высотой 3 символа:          │Button        │
                                      └──────────────┘

                                      ┌──────────────┐
                                      │              │
   Кнопка высотой более 3 символов:   │Button        │
                                      │              │
                                      └──────────────┘
```

# Исследование

1. **Кнопка не имела собственной отрисовки** — `_render_block()`
   (Python) / `renderBlock()` (JS) обрабатывали её как любой блок с
   рамкой: `_draw_border()` + `_draw_content()`. Нужен отдельный путь
   отрисовки (по аналогии с `_draw_line()` из задачи 0014), а не
   переиспользование `_draw_border()`.
2. **Правила формы из примеров**:
   - верхняя рамка — только при `h >= 3`;
   - нижняя рамка — при `h >= 2`;
   - боковые рамки — `│` при `h >= 2`, `[`/`]` при `h == 1`;
   - строка label — `(h-1)//2` (0-based от верха блока): h=1,2 → 1-я
     строка, h=3 → 2-я, h=4 → 2-я, h=5 → 3-я (для чётной h — верхняя
     средняя).
3. **Label — одна строка** — у кнопки подпись, а не многострочный
   контент: перенос слов (`_wrap_text()`) для неё не применяется, текст
   обрезается по внутренней ширине, `\n` игнорируются.
4. **`border_style`** — символы рамки берутся из карты `BORDERS` (как у
   всех блоков); для `h=1` всегда ASCII `[`/`]` (однострочного
   box-drawing-аналога нет); `none` — только label без рамки.
5. **Противоречие в редакторе** — `_blockDefaults('button')` давал
   `height: 1`, а clamp в `onCanvasMouseMove()`/`_commitBlockResize()`
   ставил `minH = 2` для всех блоков, кроме `hline`: кнопку высотой 1
   нельзя было сохранить после resize. Минимум ослаблен до 1.
6. **API валидации размеров не имеет** — `BlockCreate`/`BlockUpdate`
   принимают любые `width`/`height`; серверные изменения не
   потребовались.
7. **Parity обязательна** — форматы Python и JS должны совпадать
   побайтово; правило реализовано идентично в обоих рендерерах и
   покрыто parity-тестом.

# Выполнение задачи

Изменено 2 рендерера, редактор, 3 тестовых файла + AGENTS.md:

**`boxframe/services/renderer.py`**:
- `_render_block()` — ветка для `button`: вызывает `_draw_button()` и
  возвращается (кнопка — лист, дети не рендерятся, как у линий).
- Новый `_draw_button(block, style)` — clamp к сетке (логика как в
  `_draw_border()`), затем:
  - `h == 1`: `[`/`]` по краям строки;
  - `h >= 2`: боковые `style["v"]` по всем строкам, нижняя рамка
    (`bl`/`br` + `h`); при `h >= 3` — верхняя рамка;
  - label: строка `y + (h-1)//2`, первая строка контента, обрезка по
    внутренней ширине (`w-2` при рамке, `w` при `none`).

**`boxframe/static/js/core/renderer.js`**:
- `drawButton()` — побайтовое зеркало `_draw_button()`
  (`Math.floor((h-1)/2)` ≡ `(h-1)//2`); вызывается из `renderBlock()`
  перед общей логикой рамки.

**`boxframe/static/js/editor.js`**:
- `_blockDefaults('button')` — `width: 12 → 16` (новый блок выглядит
  ровно как в примере: `[Button        ]`).
- Min height при resize кнопки — 1 (было 2): в живом превью
  (`onCanvasMouseMove`) и в `_commitBlockResize()`.

**Тесты**:
- `tests/test_renderer.py` — 10 тестов: точные строки для h=1/2/3/4/5,
  стили (dashed h=2, double h=3, h=1 для всех стилей), `none`, обрезка
  label без переноса, игнор `\n`, пустой label.
- `tests/js/test_renderer.js` — зеркала всех 10 тестов.
- `tests/test_js_renderer_parity.py` — `test_parity_button_heights`:
  кнопки h=1/2/3/5 в разных стилях + `none` с длинным label, побайтовое
  сравнение Python и JS.

**`AGENTS.md`** — в секции «Блоки» зафиксированы правила формы кнопки
со ссылкой на спецификацию.

# Замечания

1. **Кнопка — листовой компонент** — как `hline`/`vline`: дети
   (если они заданы через API) не рендерятся. Если в будущем кнопке
   понадобятся вложенные блоки — отдельная задача (отрисовка детей
   внутри формы кнопки).
2. **`[`/`]` для h=1 не зависят от стиля** — осознанный выбор:
   однострочного box-drawing-аналога нет, а `[label]` — канонический
   вид кнопки. Если понадобится «стилизованная» однострочная кнопка
   (например `║label║` для double) — меняется одна ветка в
   `_draw_button()`/`drawButton()`.
3. **HTML-оверлей кнопки не изменён** — рамка-индикатор границ
   (`block-border--*`) остаётся полной коробкой при любой высоте; это
   affordance выделения/resize, а не дубль ASCII. Если визуальное
   расхождение с `[label]`/формой без верхней рамки станет
   заметным — добавить CSS-класс `block-button` с обрезкой рамки.
4. **Label обрезается, а не переносится** — осознанный выбор:
   перенос подписи кнопки в несколько строк ломает семантику
   «кнопка = одна строка». Если понадобится многострочный label —
   это новый тип блока, а не расширение `button`.
5. **Дефолтная ширина 16** — взята из примера спецификации
   (`[Button        ]`); при необходимости легко меняется в
   `_blockDefaults()`.
