# Суть проблемы

В редакторе можно было выгрузить макет (Export → JSON/MD/ASCII), но не было
обратного пути — импорта макета из JSON-файла. Это асимметрия: макет,
созданный в другом месте или сгенерированный ИИ-агентом (одна из ключевых
целей проекта — машиночитаемый, самодокументируемый формат), нельзя было
загрузить обратно в редактор для доработки. Экспорт без импорта — это
«только выход»: полученный JSON можно было только скачать, но не вернуть в
редактор.

Кроме того, формат экспорта JSON не нёс z-порядка блоков (поле `order`
отсутствовало), а порядок блоков в экспорте — это порядок вставки в БД
(отношение `Layout.blocks` без `order_by`), а не порядок отрисовки. Любая
реализация импорта «как есть» теряла бы слои — round-trip (export → import)
был бы некорректным.

# Задача

Добавить в редактор импорт макета из JSON-файла (в обоих режимах — web и
static):

- кнопка Import открывает выбор файла;
- разобрать вложенный экспорт (`type`/`metadata`/`children`) в плоское
  представление редактора;
- если редактор не пуст — спросить: добавить блоки из файла к содержимому
  или заменить всё содержимое макетом из файла;
- импорт должен быть отменяемым (участвовать в undo/redo как одно действие);
- round-trip (export → import) должен сохранять z-порядок.

# Исследование

1. **Применение состояния уже есть — `replaceState`.** Обёртка `withHistory`
   (задача 0027) уже экспортирует `replaceState(state)`, которая адаптивно
   ходит в `store.replaceState` (local) или batch `PUT /blocks` (fetch).
   Импорт — это по сути «применить чужое состояние», поэтому вся механика
   (включая запись в undo/redo) получена бесплатно: один вызов
   `replaceState` = одна запись истории.
2. **Формат экспорта вложенный, редактор — плоский.** Экспорт
   (`export_json` / `buildExportJson`) отдаёт корневые блоки с вложенными
   `children` и именами полей `type`/`metadata`; редактор и store работают с
   плоским списком `block_type`/`meta`/`parent_id`. Нужен мост (парсер),
   который разворачивает дерево и переводит имена полей.
3. **`order` в экспорте отсутствовал — round-trip ломал z-порядок.** Порядок
   блоков в экспорте = порядок вставки в БД, а не z-порядок. Решение:
   добавить `order` в экспорт (Python + JS, backward-совместимо — просто
   доп. поле) и в парсере предпочитать явный `order`, а при его отсутствии
   (старые файлы) присваивать по порядку документа.
4. **Коллизии id при «добавлении».** При добавлении блоков из файла к
   существующим их id могли совпасть с id текущих блоков (PK-конфликт,
   путаница в UI). Решение: при импорте всегда генерировать новые id и
   пересчитывать `parent_id`-ссылки внутри импортируемого набора (idMap). В
   режиме «заменить» новые id тоже безопасны (всё равно полная замена).
5. **Слои при «добавлении».** Импортированные блоки должны оказаться поверх
   существующих. Решение: сдвинуть их `order` выше текущего максимума по
   всем блокам (z-порядок в рендерере глобальный).
6. **Размеры макета.** В режиме «заменить» применяются размеры из файла; в
   режиме «добавить» сохраняются текущие (блоки просто добавляются внутрь
   существующего холста). Для этого редактору пришлось начать отслеживать
   `layoutWidth`/`layoutHeight` (раньше он хранил только блоки).
   Ограничение: в web-режиме `replaceBlocks` меняет только блоки, размеры
   макета не трогаются (нет роута `PUT /api/layouts/{id}`).

# Замечания

1. **Store-абстракция + история окупилась в четвёртый раз.** Как в
   0025/0026/0027, новая возможность добавлена точечно: парсер в отдельном
   модуле, два метода в редакторе, кнопка в шаблоне. Логика мутаций не
   тронута; оба режима (web/static) получили импорт «бесплатно» —
   `replaceState` адаптивно ходит в local-стор или batch-эндпоинт, а запись
   в undo/redo — работа обёртки.
2. **Импорт — одно undo-действие.** Весь импорт (и «добавить», и
   «заменить») — один вызов `replaceState`, значит один Ctrl+Z откатывает
   его целиком. Это сильнее, чем по-блоки (N записей), и соответствует
   ожиданию «я импортировал файл — хочу отменить всё разом».
3. **`order` добавлен в экспорт — round-trip теперь корректен.** Старые
   JSON-файлы (без `order`) по-прежнему импортируются (order присваивается
   по порядку документа). Это backward-совместимое расширение формата;
   парсер учитывает оба варианта.
4. **Ограничение web-режима: размеры не импортируются.** `replaceBlocks`
   меняет только блоки; чтобы импортировать width/height в web-режиме,
   нужен роут `PUT /api/layouts/{id}` (схема `LayoutUpdate` уже есть, но
   роута нет). В статическом режиме размеры применяются. Отложить как
   отдельную задачу, если понадобится.
5. **Подтверждение через `confirm` (OK/Cancel).** Два варианта
   (добавить/заменить) уложены в нативный диалог: OK = добавить, Cancel =
   заменить; текст диалога это явно прописывает. Альтернатива (собственный
   модал с кнопками «добавить/заменить/отмена») была бы нагляднее, но это
   новый UI-компонент; для MVP достаточно `confirm` (как в delete/clear).
6. **Валидация на входе.** Невалидный JSON, отсутствие `blocks[]`, пустой
   набор — все дают `alert` и не трогают макет. Парсер строг к структуре,
   но прощает отсутствующие опциональные поля (дефолты).
