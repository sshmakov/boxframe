# Суть проблемы

В редакторе не было отмены действий: каждая мутация (создание,
перемещение, ресайз, смена стиля/контента/порядка, удаление, очистка
макета) сразу фиксировалась в store (а в web-режиме — в БД) и
неотвратима. Случайное удаление блока или нажатие Clear (даже с
подтверждением) означали потерю работы — единственный «восстановить»
было перерисовать макет руками. Для редактора макетов это базовый
UX-дефицит: без undo/redo работа с холстом требует постоянной
осторожности, а эксперименты («а что если сюда?») невозможны.

# Задача

Добавить в редактор действия `Undo`/`Redo` с неограниченным буфером
отменяемых команд:

- работают в обоих режимах (web с бэкендом и static без бэкенда);
- покрывают все мутации: create, update (x/y/w/h/контент/стиль/
  порядок), delete, clear;
- буфер без лимита по числу шагов;
- UI: кнопки в тулбаре + горячие клавиши Ctrl+Z / Ctrl+Shift+Z /
  Ctrl+Y;
- посимвольный ввод в properties-панели не должен засыпать буфер
  отдельными записями (coalescing).

# Исследование

1. **Все мутации сходятся в одну точку.** `editor.js` не ходит в
   fetch напрямую — только через async-интерфейс store
   (`createBlock`/`updateBlock`/`deleteBlock`/`clear`), а состояние
   макета — маленький JSON-документ `{width, height, blocks[]}`.
   Это делает snapshot-историю дешёвой и надёжной: не нужно писать
   инверсию каждой операции (command pattern), `clear` и смена
   порядка работают «из коробки», «неограниченный буфер» — просто
   JS-массив (снапшот макета на сотни блоков — десятки КБ).
2. **Рассмотренные варианты.** (а) Snapshot-стеки — выбран;
   (б) command pattern с инверсными операциями — в web-режиме undo
   не требовал бы нового эндпоинта, но инверсию надо писать под
   каждую операцию (swap в `moveBlockOrder` — неочевидна), больше
   кода и крайних случаев при выигрыше сомнительном для такого
   маленького состояния; (в) серверный undo-лог (таблица +
   эндпоинты) — история переживала бы reload и работала между
   вкладками, но объём работ (миграция, API, схемы) избыточен для
   MVP; оставлен как эскалация, если понадобится «бессмертная»
   история.
3. **Проблема web-режима.** Снапшот надо применить через API, а
   «replace all» не существовало. Выбран batch-эндпоинт
   `PUT /api/layouts/{id}/blocks` (один запрос на undo) вместо
   diff-подхода (N запросов create/update/delete без нового
   эндпоинта, но больше кода). Id блоков из снапшота передаются в
   payload и сохраняются — восстановленные блоки сохраняют
   идентичность.
4. **Coalescing обязателен.** `updateSelectedContent` срабатывает на
   каждый символ в properties-панели — без слияния буфер забьётся
   посимвольно. Решение: consecutive-обновления одного блока в окне
   500 мс = одна запись (хранится первый снапшот серии — undo
   откатывает всю серию целиком).
5. **SQLAlchemy identity map (поймано на тесте).** Первая
   реализация `replace_blocks()` делала bulk-`delete()` + вставку.
   При `expire_on_commit=False` сессия держала старый `Layout` с
   загруженной коллекцией `blocks`: ответ endpoint строился из
   устаревшей коллекции, а повторная вставка блока с тем же id
   конфликтовала с объектом в identity map (новый инстанс
   молча отбрасывался). Лечение: ORM-удаление (дети до родителей —
   иначе каскад `children` удалил бы их дважды) + `expire_all()`
   после commit перед возвратом layout.
6. **GET-снапшот на каждую мутацию ломал e2e и удваивал задержку.**
   Вторая реализация брала предмутационный снапшот через
   `store.load()` (GET) перед каждой операцией. В web-режиме это
   (а) лишняя сетевая туда-обратно на каждое действие, (б) гонка:
   inline-редактор закрывается синхронно, а PUT улетает только после
   GET — e2e-тест читал БД до прихода PUT и падал. Решение: кэш
   состояния в обёртке — seed от собственных `load()`-вызовов
   стора (редактор грузит макет на init и после каждого
   undo/redo), синк от результатов мутаций (созданный/обновлённый
   блок, удалённый id). Итог: мутация = ровно 1 запрос,
   undo/redo = ровно 1 (batch PUT в web, 0 в static).

# Выполнение задачи

Изменено 7 исходных файлов + 3 тестовых, добавлено 2 новых файла.

**`boxframe/services/layout_service.py`**
- `replace_blocks(layout_id, blocks) -> Layout`: `get_layout` (404-
  проверка на роуте), ORM-удаление существующих блоков (дети до
  родителей), вставка новых (id из payload или новый uuid,
  нормализация hline/vline), `commit`, `expire_all()`, возврат
  свежего layout.

  подстановка снапшота с deep-copy, `mutate()` (persist в

  обёрнутый `load()` сидирует кэш;

# Замечания

1. **Store-абстракция окупилась в третий раз.** Как в 0025/0026,
   новая возможность добавлена точечно: редактор получил обёртку
   store, два метода и хоткеи; логика мутаций не тронута. Оба
   режима (web/static) получили undo/redo бесплатно — обёртка
   не знает о режиме, а restore адаптивно ходит в `replaceState`
   или batch-эндпоинт.
2. **История в web-режиме живёт в памяти вкладки** (теряется при
   reload). Это осознанное ограничение выбранного варианта; если
   понадобится персистентная история — серверный undo-лог
   (вариант в «Исследование» №2), отдельная задача.
3. **Кэш состояния — источник снапшотов, а не `load()`.** Мутация
   стоит ровно 1 запрос, undo/redo — ровно 1. Кэш сидируется от
   `load()` (init, post-undo/redo) и синхронизируется от
   результатов операций. Риск: при расхождении состояния
   сервера и редактора (параллельные вкладки) снапшот будет
   неактуален — для MVP (один пользователь, без concurrent
   editing) приемлемо.
4. **Попутно выявлен предсуществующий недочёт `moveBlockOrder`.**
   При свапе порядка редактор отправляет на сервер новый order
   только перемещённого блока; порядок «соседа» меняется лишь
   локально (после reload — дубликаты order, которые
   `_normalize_block_orders` перенумерует). Undo/redo это не
   ухудшает (снапшот и restore — полные состояния), но сам swap
   стоит починить отдельно.
5. **Coalescing-окно 500 мс** — компромисс: короче — буфер
   засыпается сериями, длиннее — «залипают» осмысленно
   разделённые правки. Параметр настраивается
   (`options.coalesceWindowMs`), в тестах проверяется и слияние,
   и истечение окна.
6. **`clear()` стал отменяемым** — бесплатно: обёртка покрывает
   все четыре мутации, и «случайно очистил макет» теперь
   восстанавливается одним Ctrl+Z.
