# Суть проблемы

`grid` — «только имя» (аудит todo-0001, 2026-10-22): отрисовка идентична
`box` (общий путь `_draw_border()` + `_draw_content()`), дефолт 20×3 с
текстом `[grid]`, логики сетки нет — ни перегородок, ни ячеек. В бэклоге
(todo-0001, приоритет 1) открыто решение: «`grid`: реализовать рендер сетки
(параметры в `meta`, например `{"cols": 3}`: отрисовка внутренних
перегородок) или убрать из палитры». Замечание 4 todo-0001: параметры сетки
(число колонок/рядов) разумно хранить в `meta` — это устоявшееся место
расширенных свойств (fill/стрелки/выравнивание уже там).

Есть два источника требований к `grid`, и они совместимы:

1. **Аудит todo-0001** — `grid` должен получить «рендер сетки»: параметры в
   `meta` (например `{"cols": 3}`), отрисовка внутренних перегородок.
2. **Дизайн-документ «Элементы boxframe.md»** (Obsidian,
   `Aa/Элементы boxframe.md`) — `grid` как **сетка раскладки**, примитив
   тира 1 «любая 2D-раскладка»: каноничная фигура — сетка 3×2; параметры
   columns/rows и gap; span для отдельных детей; «колонки/ряды
   растягиваются, gap сжимается первым». (Номера ячеек из каноничной
   фигуры и grid-auto-flow из того же документа отклонены — см. варианты
   1 и 2.)

Оба прочтения объединяются: **роль** (2D-сетка раскладки с перегородками)
определяет отрисовку, **параметры** (`meta.cols`/`rows`) определяют
структуру. «Авто-раскладка детей» (grid-auto-flow из документа) не
поддерживается в чистом виде: последовательное размещение не умеет
пропускать ячейки, разреженные раскладки (дети только в части ячеек)
невозможны. Вместо этого — **snap к ячейке** при drag (дети сохраняют
абсолютные x/y, grid — «магнит», а не ограничение) — follow-up задача
(вариант 2).

# Задача

Дать `grid` характерную отрисовку (внутренние перегородки) и параметры в
`meta`. Закрыть пункт todo-0001 по `grid` (приоритет 1).

# Варианты

## Вариант 1 — перегородки (рекомендация)

`grid` рисует внешнюю рамку + внутренние перегородки по `meta.cols` /
`meta.rows`. Параметры в `meta` (устоявшееся место, замечание 4 todo-0001).

- **meta:** `cols` (int ≥ 1, дефолт 3), `rows` (int ≥ 1, дефолт 2).
- **Рендер:** внешняя рамка (по `border_style`) + внутренние перегородки
  (вертикальных `eff_cols − 1`, горизонтальных `eff_rows − 1`) с узлами
  `┬ ┴ ├ ┤ ┼` из style map.
- **Эффективные размеры:** `eff_cols = min(cols, W)`, `eff_rows = min(rows,
  H)`, где `W×H` — внутренняя область (с рамкой `(w−2)×(h−2)`, без —
  `w×h`) — вырожденные размеры не падают (каждая колонка/ряд ≥ 1 клетки).
- **Split:** `x_i = (i·W) // eff_cols` (целочисленное деление, остаток
  распределяется вправо — детерминированно, тривиально портируется в JS).
- **Контент:** не рендерится (структурный элемент, как у линий
  `hline`/`vline`). Дефолтный content `''`. Двойной клик — не открывать
  редактор контента (контент не рендерится); закрывает вместе пункт
  todo-0001 по `hline`/`vline` (та же однострочная проверка).
- **Hint `[grid]`:** подавляется (перегородки — «идентичность» блока; hint
  пересекал бы перегородку).
- **Fill:** применяется (`grid` в `FILL_TYPES`) — fill под перегородками
  (порядок: рамка → fill → перегородки → дети).
- **`border_style`:** перегородки тем же стилем, что рамка (solid/dashed/
  dotted/double); `none` → внешней рамки нет, перегородки — solid (сетка —
  структурный элемент, её идентичность — перегородки, а не рамка).
- **Дети:** поддерживаются (контейнер) — `grid` добавляется в drop-target;
  дети рисуются поверх перегородок (контент выигрывает).
- **Autosize:** нет (размер — под контролем пользователя, как у `box`).
  Ручной resize свободный (min 1×1). `LayoutService` — без изменений.
- **Невалидный `meta`** (не int, < 1) → fallback на дефолт (3/2) —
  рендерер терпим, как `fill_char`.
- **Дефолт:** 24×8 (3 колонки × 8 клеток, 2 ряда × 4 клетки), content `''`.
- **HTML-оверлей:** без изменений (перегородки в ASCII-слое, внешняя рамка —
  общий путь `.block-border`).
- **Тесты:** оба рендерера + parity + API + store + properties + e2e.

Пример (24×8, 3 колонки × 2 ряда, внутренняя область 22×6; схематично —
точный split задаёт алгоритм и фиксируется тестами):

```
┌───────────────┬──────────────┬──────────────┐
│               │              │              │
│               │              │              │
├───────────────┼──────────────┼──────────────┤
│               │              │              │
│               │              │              │
└───────────────┴──────────────┴──────────────┘
```

Ребёнок в ячейке (рисуется поверх перегородок):

```
┌───────────────┬──────────────┬──────────────┐
│ ┌───────────┐ │              │              │
│ │   box     │ │              │              │
│ └───────────┘ │              │              │
├───────────────┼──────────────┼──────────────┤
│               │              │              │
│               │              │              │
└───────────────┴──────────────┴──────────────┘
```

## Вариант 2 — snap к ячейке (+ span) (follow-up)

Развитие варианта 1: grid — «магнит» для детей: при drag ребёнок
притягивается к границе ячейки. Дети сохраняют абсолютные x/y (абсолютное
позиционирование — основа архитектуры), grid лишь квантует позицию:
`cell = (floor((y−pad) / cell_h), floor((x−pad) / cell_w))`. Разреженные
раскладки (дети только в части ячеек) поддерживаются из коробки.

- **Почему не чистый auto-flow (grid-auto-flow из документа):**
  последовательное размещение по документному порядку не умеет пропускать
  ячейки — в сетке 3×4 первый ребёнок попадает в (1,1), второй — в (1,2),
  и ребёнка нельзя поставить в нижнюю-правую ячейку (4,3), оставив
  остальные пустыми. `span` не помогает: span расширяет элемент от его
  позиции размещения, а размещение остаётся последовательным.
- **Snap:** в конце drag (mouseup) позиция ребёнка привязывается к
  верхнему-левому углу ближайшей ячейки (или ячейки под курсором —
  решить при спецификации follow-up задачи). Размер ребёнка не меняется
  (fixed, как сейчас).
- **Span (опционально):** `meta.col_span` / `row_span` — ребёнок занимает
  несколько ячеек от позиции snap.
- **Почему отдельно:** требует изменения UX drag&drop (snap при drop,
  live-превью во время drag) — отдельная задача.
- **Объём работ:** средний (1 задача). Отдельная задача после варианта 1.

Пример (3×4, `text` в верхней-левой ячейке (1,1), `image` в нижней-правой
(4,3), остальные ячейки пусты — разреженная раскладка):

```
┌────────┬────────┬────────┐
│ [text] │        │        │
├────────┼────────┼────────┤
│        │        │        │
├────────┼────────┼────────┤
│        │        │        │
├────────┼────────┼────────┤
│        │        │ [image]│
└────────┴────────┴────────┘
```

## Вариант 3 — пресет: box + hline/vline

Кнопка «grid» в палитре создаёт композицию: box + (cols−1) vline +
(rows−1) hline как детей. Рендерер не меняется.

- Минимальный, но данные не несут `cols`/`rows` (структура «теряется»),
  линии — независимые блоки (структуру легко «сломать» — сдвинуть линию, и
  сетка перестаёт быть сеткой), путь к варианту 2 закрыт.
- **Не рекомендуется.**

## Вариант 4 — убрать из `BLOCK_TYPES`

- Роль закрывает `box` + ручные линии.
- Противоречит Obsidian-документу (тир 1, «любая 2D-раскладка»).
- Удаление макеты не ломает (`block_type` в БД — свободная строка,
  неизвестные типы падают на общий путь отрисовки), но существующие `grid`
  останутся «мёртвыми» box'ами.
- **Не рекомендуется.**

# Исследование (факты из кода, 2026-10-30)

1. `grid` — общий путь в обоих рендерерах: ветки для него нет ни в
   `_render_block()` (`services/renderer.py`), ни в `renderBlock()`
   (`core/renderer.js`); рамка + word-wrap + hint + fill. `grid` в
   `FILL_TYPES` (fill применяется).
2. Дефолт 20×3 `[grid]` — fallback-ветка `_blockDefaults()` (`editor.js`),
   общая для header/footer/sidebar/input/textarea/image. Дефолтный content —
   непустая строка `[grid]` — рисуется как текст (word-wrap), а не как hint.
3. **Не контейнер в UI:** `_findDropContainer()` (`editor.js`, строка 542)
   принимает только `block_type === 'box'` — в grid нельзя перетащить
   детей. Рендерер рисует детей у любого типа
   (`_render_children_in_container` не ограничивает тип) — меняется только
   UI-фильтр (одно место; group-move использует тот же
   `_findDropContainer`).
4. Бэкенд (`LayoutService`) не имеет типоспецифичной логики для `grid`
   (только `hline`/`vline` — толщина, `text` — точный fit, `button` — fit,
   `divider` — autosize-рост) — **менять не нужно** (autosize нет).
5. `meta`: `fill` (FILL_TYPES включает `grid`), `text_align`,
   `vertical_align` — уже в `properties.js` (`grid` в списках типов обоих
   свойств). `cols`/`rows` — новые.
6. HTML-оверлей: `.block-inner` прозрачный (без фона), `.block-border` —
   outline поверх ASCII; общий путь генерирует `.block-border` для `grid` →
   **HTML-правки не нужны** (перегородки — в ASCII-слое, внешняя рамка —
   общий путь). Класс `block-grid` генерируется, но не стилизован
   (мёртвый класс, todo-0001) — оставить или убрать.
7. Двойной клик — `onCanvasDblClick()` (`editor.js`) открывает редактор
   контента для любого блока; тип-чек добавляется после `_blockAt`.
8. Дети рисуются после контента родителя (`_render_block`: рамка → контент →
   дети); абсолютный rect ребёнка = `parent.x + 1 + child.x, parent.y + 1 +
   child.y` (1-cell padding) — дети рисуются поверх перегородок.
9. E2e: `test_editor.py` захардкожено 14 кнопок статической палитры (2
   места); `test_drag_drop.py` берёт `len(BLOCK_TYPES)` (автоматически
   подстраивается). Палитра не меняется (14) — правки e2e-счётчиков не
   нужны.
10. Специфичных тестов у `grid` нет (todo-0001, п. 8).
11. Style map `BORDERS[style]` имеет узлы `t_t` (┬), `b_b` (┴), `t_l` (├),
    `t_r` (┤), `b_b` (┼) — перегородки используют их.
12. Существующие `grid` в макетах (если есть) изменят вывод: вместо текста
    `[grid]` — перегородки. Данные не теряются; миграция не делается
    (тип «только имя», осмысленного использования нет).
