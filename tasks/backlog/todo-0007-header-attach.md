# Суть проблемы

`header` — «только имя» (аудит todo-0001, 2026-10-22): отрисовка
идентична `box` (общий путь `_draw_border()` + `_draw_content()`),
дефолт 20×3 с текстом `[header]`, характерной отрисовки нет. Входит в
группу «только имя» вместе с `footer`/`sidebar` (`content` закрыт,
todo-0004; `grid` закрыт, todo-0005).

Предлагаемая доработка: когда `header` вставлен **дочерним в `box`** и
прижат к верхней стороне, он «прилипает» к верху — отключаются
верхняя, левая и правая стороны рамки, остаётся только нижняя, и она
соединяется (junction) с рамкой `box`. Визуально `header` «сидит»
сверху содержимого `box`, отделённый от него линией:

```
┌────────────────┐
│ header         │
│                │
├────────────────┤
│                │
└────────────────┘
```

# Задача

Дать `header` характерную отрисовку в режиме «приклеен к верху
`box`»: без верхней/левой/правой рамки, только нижняя линия на всю
внутреннюю ширину `box` и junctions с рамкой `box`. Закрыть пункт
todo-0001 по `header` (приоритет 2).

# Варианты

## Вариант 1 — геометрический, проверка по `y` (рекомендация)

`header` в режиме «attached», когда его **относительная** `y <= 0`
(верхний край на уровне верхней внутренней границы `box` или выше).
`x` и `width` **не проверяются**. Родитель — только `box` (`grid` вне
scope, см. замечание 3).

- **Эффективная геометрия (выводится при рендере):** `x=0`, `y=0`
  (относительные), `width` = внутренняя ширина `box` (`bw−2`),
  `height` = сохранённая высота. Сохранённые `x`/`width` игнорируются,
  пока `header` приклеен; они важны только когда `header` отклеен
  (`y>0`) — тогда он рендерится как обычный `box` в сохранённой
  позиции/ширине.
- Это render-time вывод (как перегородки `grid`, todo-0005), а не
  изменение данных. При resize `box` `header` автоматически следует за
  шириной — сохранённые данные не трогаются.
- **Обратная совместимость:** старый макет, где `header` *случайно*
  лежит при `y=0` в `box`, будет рендериться иначе (без трёх сторон
  рамки). Вероятность мала; формальное отклонение от правила
  обратной совместимости — согласовано как исключение (см. замечание 2).

## Вариант 2 — флаг в `meta`

`meta.attach: "top"`, ставится при вставке.

- Плюсы: строгая обратная совместимость, состояние явное.
- Минусы: флаг может «протухнуть» (перемещённый `header` висит
  посреди `box` без трёх сторон рамки — выглядит сломанно); нужна
  UI-точка управления флагом; больше кода. По сути — ограниченное
  воскрешение per-side границ, удалённых в 0051-фазе 1.

## Сравнение

| | 1 — геометрический (y) | 2 — флаг |
|---|---|---|
| Условие | 1 проверка (`y<=0`) | флаг в `meta` |
| Обратная совместимость | `header` при `y=0` рендерится иначе (редко) | строгая |
| Переприклеить после drag | просто (достаточно `y=0`) | нужен флаг |
| Узкий `header` | нет — всегда на всю ширину | нет |
| Объём кода | меньше | больше (флаг + UI + stale) |
| Рекомендация | **да** | нет |

# Ключевые решения (согласованы)

1. **Условие:** относительная `y <= 0`; родитель — только `box`
   (`grid` вне scope).
2. **Растяжение:** приклеенный `header` всегда на всю внутреннюю
   ширину `box` — узкого `header` нет. Эффективная геометрия
   `x=0, y=0, w=inner_w`.
3. **Стиль линии:** свой `border_style` `header`'а; junctions —
   стандартные `├`/`┤` (style map родителя), как в `grid` (0063).
4. **Родитель без рамки** (`border_style=none`): attached-режим
   работает, но junctions нет (линия просто заканчивается `─`).
5. **Дефолтная высота:** 3 (текущий дефолт, не меняется).
6. **Sticky при resize `box`:** `header` следует за шириной
   (render-time), сохранённые данные не трогаются.
7. **`grid` как родитель:** вне scope — `header` внутри `grid`
   рендерится как сейчас (общий путь).
8. **Resize ширины attached-`header`:** сохранённый `width`
   игнорируется, пока приклеен, применяется после отклейки
   (`y>0`).

# Правила рендера

Обозначения: родитель-`box` — абсолютные `(px, py)`, размер
`(pw, ph)`. Внутренняя область — `x ∈ [px+1, px+pw−2]`,
`y ∈ [py+1, py+ph−2]`; `inner_w = pw−2`, `inner_h = ph−2` (1-cell
padding — безусловный, как в `_render_children_in_container`).
`header`-ребёнок — относительные `(cx, cy)`, размер `(cw, ch)`.
**Attached** ⇔ `cx` не проверяется, `cy <= 0`, родитель — `box`.

Эффективная геометрия (абсолютная): `x = px+1`, `y = py+1`,
`w = inner_w`, `h = ch`.

- **Рамка:** верхней/левой/правой сторон нет.
- **Нижняя линия:** строка `py+ch`, столбцы `px+1 .. px+pw−2` (вся
  внутренняя ширина). Символ — `border_style` `header`'а. Рисуется,
  только если `ch <= inner_h` (строка линии внутри внутренней
  области) и `border_style != none`. При `ch > inner_h` линия
  клипнута (не рисуется) — нижнюю границу визуально задаёт рамка
  `box`.
- **Junctions:** на рамке `box` в клетках `(px, py+ch)` и
  `(px+pw−1, py+ch)` — `├`/`┤` (style map `box`'а). Рисует **родитель**
  (линия `header`'а клипнута во внутреннюю область и не может
  дописать клетки рамки). Рисуется, только если линия рисуется
  (`ch <= inner_h`, `border_style header != none`) **и** у `box` есть
  рамка (`border_style != none`). При совпадении строки линии с
  последней внутренней строкой (`ch == inner_h`) junctions заменяют
  боковые `│` — корректно.
- **Контентная область:**
  - `border_style != none` — полная ширина (`inner_w`) × `ch−1` строк
    (строки `py+1 .. py+ch−1`, над линией);
  - `border_style == none` — полная ширина × `ch` строк (линии нет,
    высота полная).
  - Контент word-wrap по `inner_w` + `meta.text_align`/
    `vertical_align`; fill (`meta.fill`) заливает область; hint
    `[header]` при пустом контенте — как у `box`.
- **`ch == 1`** (`border_style != none`) — контентная область 0 строк,
  `header` = только линия (разделитель, приклеенный к верху).

Примеры (box 20×8, внутренняя 18×6; `header` h=3, content `[header]`):

```
Приклеен (y=0):                 Отклеен (y=2, обычный box):
┌──────────────────┐            ┌──────────────────┐
│ [header]         │            │                  │
│                  │            │ ┌──────────────┐ │
├──────────────────┤            │ │ [header]     │ │
│                  │            │ └──────────────┘ │
│                  │            │                  │
│                  │            └──────────────────┘
└──────────────────┘
```

# Исследование (факты из кода)

1. `header` — общий путь в обоих рендерерах: ветки для него нет ни в
   `_render_block()` (`services/renderer.py`), ни в `renderBlock()`
   (`core/renderer.js`); рамка + word-wrap + hint + fill.
2. Дети клипуются во внутреннюю область родителя
   (`_render_children_in_container` / `renderChildrenInContainer`):
   ребёнок не может написать в клетки рамки родителя → junctions
   обязан рисовать **родитель** (паттерн frame-узлов `grid`, 0063).
3. Junction-логика уже существует для перегородок `grid`
   (`_grid_junction`, 0063): frame-узлы рисует сам контейнер по
   реально отрисованным сегментам.
4. Per-side границы (`meta.border_h`/`border_v`) удалены 2026-10-16
   (0051-фаза 1) — это type-specific поведение `header`, а не общий
   механизм сторон рамки (см. замечание 1).
5. `_blockDefaults('header')` — fallback 20×3 `[header]` (`editor.js`);
   путь создания: drag → `onCanvasDrop` (позиция дропа + контейнер по
   центру), клик по палитре → `addBlock` (1,1).
6. `_absoluteRect(block)` (`editor.js`) — центральная точка
   абсолютной геометрии: используется в hit-test (`_blockAt`),
   selection frame (`_selectionBBox`), drag-превью, drop-target.
   Эффективная геометрия attached-`header` встраивается сюда — все
   потребители получают её автоматически.
7. HTML-оверлей генерируется из сохранённых dict
   (`_block_preview_html` / JS-аналог), рамка — `.block-border--{style}`
   (полный `outline`). Для attached-`header` нужна нижняя линия вместо
   полного outline (новый CSS-класс) и позиционирование по эффективной
   геометрии.
8. Бэкенд (`LayoutService`): типоспецифичной логики для `header` нет —
   **менять не нужно** (редактор шлёт готовые координаты).

# Follow-up

**Несколько attached-`header` в одном `box`** — отдельная задача:
приклеенные `header` выстраиваются по высоте друг за другом согласно
z-order (каждый — под нижней линией предыдущего). В задаче 0074
несколько attached-`header` рендерятся независимо (линии могут
пересекаться) — наложение не обрабатывается специально.

# Замечания

1. Это ограниченное воскрешение per-side границ (удалены в 0051-фазе 1)
   — но как **type-specific поведение `header`**, а не общий механизм
   сторон рамки. Зафиксировано, чтобы не расползалось.
2. **Обратная совместимость (вариант 1):** старый макет, где `header`
   лежит при `y=0` в `box`, рендерится иначе. Вероятность мала;
   согласовано как исключение из правила обратной совместимости.
3. Кросс-ссылки: todo-0001 (приоритет 2, семантическая группа + пункт
   `header`), 0063 (junctions `grid`), 0051-фаза 1 (per-side границы
   удалены), todo-0005 (`grid`, render-time вывод геометрии).
4. **Зачем `x = px+1` (а не `px`) в эффективной геометрии** — прояснение
   (2026-11-11). Не путать с «защитой рамки от затирания»: дети клипнуты
   во внутреннюю область (`_render_children_in_container`, `self._clip =
   inner`), и это работает **одинаково** для приклеенного и обычного
   ребёнка. Поэтому даже обычный `header`, лежащий при `x = px`
   (относит. `cx = −1`), НЕ затирает левую рамку `box` — его левая
   рамка/линия в клетке `px` просто обрезаются клипом. `+1` нужен не для
   защиты рамки, а потому что из `x`/`width` **выводятся** не только
   линия: (а) content-area = `x`/`width` — word-wrap и выравнивание
   считаются по ней; при расширении rect в клетки рамки `content_w =
   inner_w+2`, текст центрируется/переносится по большей ширине и затем
   обрезается клипом → съедает по символу слева/справа, центрирование
   смещается; (б) HTML-оверлей (`_attached_line_html`/`attachedLineHtml`)
   позиционируется по эффективной геометрии — расширение в клетки рамки
   рассогласует HTML-слой с ASCII.
   - **Расширять приклеенный `header` влево/вправо в клетки рамки
     бессмысленно:** линия рисуется ребёнком и клипнется до
     `px+1 .. px+pw−2` (тот же результат); стыки `├`/`┤` в `px` и
     `px+pw−1` и так рисует **родитель** (`border_ops`, до сужения
     клипа) — ребёнок туда писать не может. Визуальный выигрыш = 0, а
     content/HTML-геометрия портятся.
   - **Расширять «вверх» — меняет результат:** нижняя линия привязана к
     `row = ey+eh−1`, родитель ставит `├`/`┤` по той же `ey+eh−1`
     (согласовано). Сдвиг rect вверх (`ey = py`) поднимает разделяющую
     линию на строку и загоняет верх body в строку верхней рамки `box`
     (`┌──┐`, клипнется) — теряется usable-строка контента.
   Итог: `x = px+1, width = inner_w` — точная привязка к истинной
   внутренней области, из которой корректно выводятся и линия (переживает
   клип), и wrap/align контента, и HTML-геометрия, и стыковка с junctions
   родителя. Рамку в обоих сценариях бережёт один и тот же клип.
