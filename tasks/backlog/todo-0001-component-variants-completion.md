# Суть проблемы

Из 14 типов блоков в `BLOCK_TYPES` реально работают по назначению только 4:
`box`, `text`, `hline`, `vline`. Остальные — либо семантические имена без
характерной отрисовки, либо не доделаны:

- `divider` дублирует роль `hline`, но рендерится как обычный блок с полной
  рамкой (пробел зафиксирован в задаче 0014, не закрыт);
- `grid` не имеет никакой логики сетки — рендерится как обычный `box`;
- `button` создаётся с дефолтной высотой 1: в ASCII рамка не рисуется
  (рендерер требует h≥2), блок выглядит как голый текст, а в HTML-превью
  рамка видна — несогласованность между двумя представлениями;
- `input`, `textarea`, `image` не имеют характерной отрисовки
  (подчёркивание/курсор, плейсхолдер изображения);
- `header`, `footer`, `sidebar`, `content` — только имена: отрисовка
  идентична `box`, семантических дефолтов (полная ширина, позиция, пропорции)
  нет.

Плюс сквозные пробелы: API не валидирует `block_type`/`border_style`, в UI
нет способа создать вложенные блоки, поле `meta` нигде не используется,
есть мёртвый код.

# Задача

Привести набор компонентов к согласованному состоянию: каждый тип в палитре
либо рендерится характерным для себя образом, либо убирается из
`BLOCK_TYPES`. Закрыть сквозные пробелы (валидация, вложенность, мёртвый код).

# План работ

## Приоритет 1 — сломанные и дублирующие типы

- [ ] `divider`: решение — убрать из `BLOCK_TYPES` (роль закрывает `hline`)
      или дать отрисовку линии; обновить палитру и тесты
- [ ] `grid`: реализовать рендер сетки (параметры в `meta`, например
      `{"cols": 3}`: отрисовка внутренних перегородок) или убрать из палитры
- [ ] `button`: устранить несогласованность рамки — дефолтная высота 3
      (рамка в обоих представлениях) либо особая отрисовка (например
      `[Button]` с центрированием); тесты

## Приоритет 2 — характерная отрисовка

- [ ] `input`: отрисовка с подчёркиванием/курсором (например, нижняя линия
      и `▌` в начале)
- [ ] `textarea`: рамка с многострочным плейсхолдером
- [ ] `image`: плейсхолдер (диагональный X по углам или штриховка)
- [ ] `header`/`footer`: семантические дефолты (полная ширина, позиция
      сверху/снизу)
- [ ] `sidebar`: дефолт узкий и высокий
- [ ] Тесты по типам в `tests/test_renderer.py` (сейчас специфичных тестов
      нет ни у одного из этих типов)

## Приоритет 3 — сквозные пробелы

- [ ] API: валидация `block_type` по `BLOCK_TYPES` и `border_style` по
      `BORDER_STYLES` (Pydantic `Literal`/`field_validator`, 422 на
      неизвестные значения)
- [ ] UI: вложенность — drag-to-nest или действие «сделать дочерним» в
      списке элементов (бэкенд уже поддерживает `parent_id`, рендерер —
      `children`)
- [ ] `meta`: либо UI для редактирования, либо убрать поле из модели/API/
      экспорта
- [ ] Двойной клик: не открывать редактор контента для `hline`/`vline`
      (контент линии никогда не рендерится)
- [ ] Мёртвый код: удалить `syncFromRaw()` из `editor.js`; классы
      `block-{type}` в HTML-превью — простилзовать или убрать
- [ ] Полный прогон тестов (unit/API/e2e)

Ключевые факты:

1. Единственный особый путь отрисовки — `hline`/`vline` через
   `_draw_line()`; все остальные типы проходят общий путь
   `_draw_border()` + `_draw_content()`.
2. Типоспецифичная логика на фронте — только `_blockDefaults()` в
   `editor.js` (`button` 12×1, `hline` 20×1, `vline` 1×5, остальное 20×3).
3. Типоспецифичная логика на бэкенде — только принудительная толщина линий
   в `LayoutService.create_block`/`update_block`.
4. API принимает любую строку в `block_type` и `border_style` — валидации
   нет.
5. Вложенность (`parent_id`/`children`) поддерживается моделью, рендерером
   и экспортом, но в UI создать child невозможно; в превью дети
   флаттнятся.
6. `meta` (JSON) присутствует в модели, API и экспорте, но не используется
   ни одним типом и не редактируется в UI.
7. Класс `block-{type}` в HTML-превью не стилизован в CSS — мёртвые классы.
8. Покрытие тестами: `hline`/`vline` — 10+ специфичных тестов;
   `box`/`button`/`text`/`header`/`content` — только общие тесты;
   `grid`, `image`, `input`, `textarea`, `divider`, `sidebar`, `footer` —
   специфичных тестов нет.

# Замечания

1. Формат псевдографики (box-drawing символы) не менять — это ядро продукта.
2. Удаление типа из `BLOCK_TYPES` не ломает существующие макеты:
   `block_type` в БД — свободная строка, рендерер для неизвестных типов
   падает на общий путь отрисовки.
3. E2e-тест `test_palette_buttons_are_draggable` берёт число кнопок из
   `len(BLOCK_TYPES)` (задача 0014) — автоматически подстроится под
   удаление типов.
4. Если `grid` реализуется, параметры сетки (число колонок/рядов) разумно
   хранить в `meta` — это единственный свободный JSON-поле блока.
5. При фиксе `button` нужно согласовать оба представления: HTML-превью
   рисует рамку при любых размерах, а ASCII-рендерер требует w≥2 и h≥2.
