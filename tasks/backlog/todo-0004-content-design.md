# Суть проблемы

`content` — «только имя» (аудит todo-0001, 2026-10-22): отрисовка
идентична `box` (общий путь `_draw_border()` + `_draw_content()`),
дефолт 20×3 с текстом `[content]`, характерной отрисовки и
семантических дефолтов нет. Входит в группу «только имя» вместе с
`header`/`footer`/`sidebar`.

Есть два источника требований к `content`, и они совместимы:

1. **Аудит todo-0001** — `content` как часть семантической группы
   (header/footer/sidebar/content) должен получить «семантические
   дефолты» (размер/пропорции основной области).
2. **Дизайн-документ «Элементы boxframe.md»** (Obsidian,
   `Aa/Элементы boxframe.md`) — `content` как **плейсхолдер текста**,
   примитив тира 1 «любой текст»: строки «lorem» или штриховки `▒▒▒`,
   обрезанные по ширине; последняя строка короче — «как абзац»; перенос
   по ширине контейнера, выравнивание left/center/right, двойной клик —
   редактирование placeholder-текста. (`label` из того же документа —
   «строка текста (в отличие от content — блока)» — в boxframe играет
   тип `text`, 0049.)

Оба прочтения объединяются: **роль** (плейсхолдер текста) определяет
отрисовку, **семантический дефолт** (40×10) определяет размер по
умолчанию.

# Задача

Дать `content` характерную отрисовку (плейсхолдер текста) и
семантический дефолтный размер. Закрыть пункт todo-0001 по `content`
(приоритет 2).

# Варианты

## Вариант 1 — убрать из `BLOCK_TYPES`

- Нет замены: `box` — generic-контейнер, `text` — однострочный
  autosize-блок без рамки, а не рамочная многострочная область. В
  документе `content` — примитив тира 1.
- Удаление макеты не ломает: `block_type` в БД — свободная строка,
  неизвестные типы падают на общий путь отрисовки.
- **Не рекомендуется.**

## Вариант 2 — плейсхолдер текста + семантический дефолт
(рекомендация, объединённый)

`content` = рамочный многострочный текстовый блок: пустой — lorem-
плейсхолдер, непустой — текст пользователя (word-wrap). Дефолтный
размер 40×10 (основная область, крупнее box 20×3).

- **Рендер:**
  - **пустой контент, без fill** → **плейсхолдер**: строки lorem
    (детерминированные), перенесённые по внутренней ширине, заполняют
    внутреннюю высоту, последняя строка короче — «как абзац».
    Рисуется тем же путём, что и контент (word-wrap +
    `meta.text_align`/`vertical_align`).
  - **непустой контент** → word-wrap + выравнивание (уже есть, без
    изменений).
  - **fill** (`meta.fill`) → подавляет плейсхолдер (как сейчас подавляет
    hint).
- **Алгоритм плейсхолдера** (оба рендерера, parity побайтово):
  - фиксированный источник — стандартный lorem (~245 символов):
    `lorem ipsum dolor sit amet, consectetur adipiscing elit, sed do
    eiusmod tempor incididunt ut labore et dolore magna aliqua. ut enim
    ad minim veniam, quis nostrud exercitation ullamco laboris nisi ut
    aliquip ex ea commodo consequat.`
  - `text = (LOREM + " ") * (h + 1)` — гарантирует ≥ h строк при любой
    ширине;
  - `lines = wrap(text, w)[:h]` (тот же word-wrap, что `_wrap_text`);
  - последняя строка укорачивается до `max(3, w * 7 // 10)` (только при
    `h ≥ 2` и `w ≥ 4`) — короче, «как абзац».
  - Плейсхолдер перегенерируется на каждом рендере из текущего размера →
    при resize строки переносятся/добавляются/отбрасываются
    («live re-layout» из документа).
- **Дефолт:** 40×10, content `''` (пустой → виден плейсхолдер),
  border `solid`.
- **meta:** без изменений — `fill`, `text_align`, `vertical_align` уже
  доступны.
- **Дети:** поддерживаются (контейнер, как у box) — без изменений.
- **Двойной клик:** существующий inline-редактор; пользователь вводит
  текст → плейсхолдер исчезает, очищает текст → возвращается.
- **Штриховка `▒▒▒`** (альтернатива из документа) — отклонена: lorem
  информативнее и AI-readable (самодокументируемый формат); штриховку
  можно добавить позже как `meta`-опцию.

Пример (40×10, внутренняя область 38×8; схематично — точные строки
задаёт алгоритм и фиксируется тестами):

```
┌──────────────────────────────────────┐
│ lorem ipsum dolor sit amet, conse    │
│ ctetur adipiscing elit, sed do eius  │
│ mod tempor incididunt ut labore et   │
│ dolore magna aliqua. ut enim ad min  │
│ im veniam, quis nostrud exercitation │
│ ullamco laboris nisi ut aliquip ex e │
│ a commodo                           │  ← последняя строка короче (~70%)
└──────────────────────────────────────┘
```

## Вариант 3 — smart placement (вне scope)

При создании блок «прилипает» к семантической позиции (под header,
справа от sidebar). Требует знания размера layout (`Layout.width/height`
опциональны) и позиций других блоков — сквозная фича для всей группы,
отдельная задача. Открытый вопрос.

# Исследование (факты из кода, 2026-10-28)

1. `content` — общий путь в обоих рендерерах: ветки для него нет ни в
   `_render_block()` (`services/renderer.py`), ни в `renderBlock()`
   (`core/renderer.js`); рамка + word-wrap + hint + fill.
2. Hint `[content]` рисуется при `not block.content and has_border and
   w >= 4 and not fill` — плейсхолдер занимает его место для `content`.
3. Дефолт 20×3 `[content]` — fallback-ветка `_blockDefaults()`
   (`editor.js`), общая для header/footer/sidebar/content/grid/
   input/textarea/image. Дефолтный content — непустая строка `[content]`
   — рисуется как текст, а не как hint.
4. Путь создания: drag → позиция дропа + `_blockDefaults`; клик по
   палитре → (1,1) + `_blockDefaults` (`addBlock`). `editor.js` общий
   для web- и static-режимов — правка одна.
5. Бэкенд: типоспецифичной логики для `content` в `LayoutService` нет
   (только `hline`/`vline` — толщина, `text` — точный fit, `divider` —
   autosize-рост) — **менять не нужно**.
6. `meta`: `fill` (FILL_TYPES включает `content`), `text_align`,
   `vertical_align` — уже в `properties.js`.
7. Контент блоков в HTML-оверлее не дублируется (живёт в ASCII-слое) →
   HTML-правки не нужны; плейсхолдер в ASCII-слое → покрыт parity.
8. Специфичных тестов у `content` нет (todo-0001, п. 8).
