# Суть проблемы

boxframe — однопользовательское приложение: нет аутентификации, у проектов
нет владельца, все маршруты открыты. Любой, кто достучался до сервера, видит
все проекты и может их менять. Это делает невозможным развёртывание на
корпоративном сервере, где пользователи должны видеть только проекты, в
которые имеют доступ.

Ключевые факты из кода (аудит 2026-09-29):

- `models/project.py` — у `Project` нет `owner_id`; таблиц `users` и
  участников нет;
- `api/projects.py`, `api/layouts.py`, page-роуты в `main.py` — все
  работают без аутентификации;
- `LayoutService.list_projects()` отдаёт все проекты без фильтра;
- `api/test_cleanup.py` смонтирован без защиты;
- БД — SQLite (MVP-фича), для многопользовательского режима
  одновременные записи и бэкапы надёжнее на Postgres;
- AGENTS.md: «Не добавлять авторизацию в MVP» — ограничение снимается
    решением о корпоративном развёртывании.

# Задача

Подготовить boxframe к развёртыванию на корпоративном сервере:
идентичность пользователей (SSO), контроль доступа к проектам
(владелец + участники с ролями) и production-деплой (Docker, Postgres,
безопасность).

- [ ] Выбор способа аутентификации: SSO на уровне прокси

- [ ] Неразрешённые запросы: HTML — редирект в IdP, API — 401
- [ ] Тесты (аутентификация, редирект, 401)

## Фаза 2 — доступ к проектам

- [ ] `Project.owner_id → users.id`; миграция существующих проектов
      под владельца-админа
- [ ] Таблица `project_members(project_id, user_id, role)`:
      `owner` / `editor` / `viewer`
- [ ] `GET /api/projects/` и страница `/` — только проекты, где пользователь
      owner/member (фильтр в `LayoutService.list_projects`)
- [ ] Запись (блоки, layout'ы, `PUT /blocks`) — `editor` и выше;
      `viewer` — только чтение и render/export
- [ ] Проверка доступа на layout-роутах через `layout.project_id`
      (иначе угадавший UUID увидит чужой макет)
- [ ] UI: страница проекта — список участников, кнопка «Пригласить»
      (по email)
- [ ] Тесты (фильтр списка, роли, 403/404 на чужие layout'ы)

## Фаза 3 — деплой и hardening

- [ ] CSRF: session-cookie `SameSite=strict` + CSRF-токен на мутации
      (HTMX шлёт заголовок `X-CSRF-Token`)
- [ ] `api/test_cleanup.py` — отключить в production
- [ ] Postgres (SQLAlchemy 2.0 — меняется только URL в `config.py`)
- [ ] Docker: uvicorn + nginx (TLS) + Keycloak (если OIDC) + Postgres,
      docker-compose
- [ ] Миграция данных при переходе на Postgres

# Исследование

## Идентичность: два варианта

**A — SSO на уровне прокси.** Корпоративный шлюз (Keycloak в режиме
reverse-proxy, nginx с `auth_request`, существующий gateway) делает логин
и подставляет `X-Forwarded-User`. Приложение читает пользователя из
заголовка; весь OIDC-флоу живёт вне boxframe.
- Плюсы: минимум кода в boxframe, логин-UX и MFA — за IdP.
- Минус: заголовок можно доверять только если прокси — единственная
  точка входа (внешний порт приложения не слушается).

**B — OIDC внутри приложения** (`authlib` / `fastapi-oidc`).
Authorization code flow: редирект в IdP (Keycloak / Azure AD / Okta),
подписанный session-cookie, валидация сессии на каждом запросе.
- Плюсы: самодостаточный, работает за любым прокси.
- Минус: больше кода (middleware + зависимости).

Рекомендация: есть SSO-шлюз → A; нет → поднять Keycloak (self-hosted,
федерация с AD/LDAP) и B.

## Модель доступа

Минимальная и понятная: владелец + явные участники.

- `owner` — создатель, полный контроль (включая удаление проекта);
- `editor` — изменение блоков/layout'ов;
- `viewer` — только чтение, render/export.

Альтернатива для больших организаций — группы из IdP (группа
Keycloak/AD → доступ к проекту): масштабируется лучше, но сложнее.
Начать с явных участников, группы — позже, если понадобится.

## Деплой

- Один контейнер (uvicorn) + nginx (TLS) + Keycloak (если B) + Postgres;
  docker-compose для старта, k8s — если компания на нём.
- SQLite с WAL выдержит небольшую команду, но Postgres безопаснее для
  многопользовательского режима (одновременные записи, бэкапы) — это
  «веская причина» из AGENTS.md сменить БД.

# Замечания

1. Фазы независимы — после каждой фазы система остаётся рабочей
   (фаза 1: все видят всё, но под своим логином).
2. Статический редактор (`static/editor/index.html`, `file://`) не
   затрагивается — он локальный, без бэкенда.
3. После фазы 1 обновить AGENTS.md: снять пункт «Не добавлять
   авторизацию в MVP», добавить секцию об аутентификации и ролях.
4. Правило «CSRF не требуется» из AGENTS.md действует только без
   cookie-сессий; с сессией CSRF-токен обязателен (фаза 3).
5. Перед стартом уточнить у заказчика: какой IdP есть в компании
   (Keycloak / Azure AD / LDAP / ничего) и сколько одновременных
   пользователей ожидается — от этого зависят выбор варианта A/B
   и SQLite/Postgres.
