# Суть проблемы

При размещении единственного элемента на верхнем краю макета (y=0) ASCII-арт
и оверлей блоков были выровнены, а при размещении элемента в середине макета
(y>0) весь арт сдвигался вверх на одну строку (14.4px) относительно оверлея,
рамки границ макета и рамки выделения.

Причина не в padding и не в рендерере: HTML-парсер по спецификации отбрасывает
первый перевод строки сразу после открывающего тега `<pre>`. ASCII-арт
инлайнится непосредственно после `<pre ...>`, поэтому когда арт начинается с
пустой строки (верхний блок не на строке 0), браузер теряет первую строку.

При проверке обнаружен второй баг: X/Y и W/H поля в панели свойств блока
не работали вовсе — `updateSelectedXY`/`updateSelectedWH` читали значения
через `e.currentTarget.querySelectorAll('input')`, а `currentTarget` — это
сам input (детей-input у него нет), поэтому значения всегда были NaN и
обработчик выходил, откатывая ввод.

# Исследование

1. **Padding по конструкции согласован** — единственный offset это 16px
   padding `.render-wrapper`; оверлеи позиционируются с
   `padding_offset = 16px`, у art-слоя нет margin/padding (глобальный reset
   `* { margin: 0; padding: 0 }`). Размер символа измеряется в браузере
   (`_measureCharSize`) и передаётся в рендерер, поэтому пиксели сетки
   совпадают с метриками шрифта.
2. **Замеры** (Playwright, chromium) — сравнивались левый верхний угол
   оверлея блока и глиф `┌` (первый непустой символ арта) в двух случаях:
   - блок на (0,0): сдвиг 0.00px;
   - блок на (0,12): сдвиг +14.50px — оверлей на строку ниже глифа.
   Расхождение позиционно-зависимое: появляется ровно тогда, когда арт
   начинается с пустой строки.
3. **Корневая причина** — HTML-парсер отбрасывает первый U+000A сразу после
   открывающего тега `<pre>` (правило спецификации, позволяющее
   «красиво» переносить содержимое pre в исходнике). Проверено в браузере:
   `<pre>\n\nAB</pre>` → `"\nAB"`, а
   `<div style="white-space:pre">\n\nAB</div>` → `"\n\nAB"`. Экранирование
   `&#10;` не помогает — сущность декодируется в character token и
   отбрасывается так же.
4. **Рендерер не виноват** — `rawText` (вывод JS-рендерера) корректен:
   блок на y=12 стоит на строке 12, первый непустой символ на индексе 12.
   Строка теряется только при парсинге разметки браузером.
5. **Затронуты оба режима** — web-режим (render-эндпоинт `api/layouts.py`)
   и static-режим (`PGRenderer.renderHtml`) генерируют одинаковую разметку
   `<pre ...>` + ASCII.

# Замечания

1. **Не возвращать ASCII-арт обратно в `<pre>`** — первая строка снова
   потеряется при любом арте, начинающемся с пустой строки. Любые будущие
   потребители render-разметки (превью-страницы и т.п.) должны использовать
   `<div class="ascii-art">`.
2. **Поля панели свойств теперь работают** — регрессионный e2e-тест
   перемещает блок именно через панель. Если изменится разметка панели
   (порядок `.prop input`), нужно обновлять `_panelInputs()` и тест.
3. **Остаточный сдвиг 0.11px** — сабпиксельное округление текстовой
   раскладки браузера (line box глифа против ожидаемых 14.4px × строка).
   Визуально не заметно; для пиксель-перфекта можно было бы учитывать
   half-leading шрифта, но это зависит от конкретного шрифта.
4. **E2E прогонялись против dev-сервера пользователя** (порт 8000,
   `--reload`) — как в задаче 0019, сервер обслуживает именно этот код
   (bind mount), поэтому результаты валидны.
5. **Предсуществующая консольная ошибка (не фиксилась, вне scope)** —
   Alpine вычисляет `selectedBlock.block_type` и прочие bindings панели
   свойств даже когда панель скрыта (`x-show` не останавливает вычисление
   выражений): при каждой загрузке страницы в консоли
   `Cannot read properties of null`. На работу не влияет; лечится
   optional chaining в шаблоне (`selectedBlock?.block_type`).
