# Суть проблемы

Вариант 1 `grid` (задача 0061) рисует перегородки, а дети рендерятся
поверх них с прозрачной внутренностью — перегородки «просвечивают»
сквозь ребёнка (замечание 3 задачи 0061). Если ребёнок занимает две (или
более) последовательные ячейки — span — линия между ними видна внутри
него, и span выглядит «разорванным» (ребёнок без рамки, span ячеек 1–2
верхнего ряда, 3×2):

```
┌───────┬──────┬───────┐
│SPAN   │      │       │   ← перегородка на колонке 8 видна
│       │      │       │     внутри ребёнка, span «разорван»
│       │      │       │
├───────┼──────┼───────┤
│       │      │       │
│       │      │       │
└───────┴──────┴───────┘
```

Пожелание пользователя (2026-10-31): если дочерний элемент занимает две
(или более) последовательные ячейки по вертикали или по горизонтали
(span), не рисовать рамку под дочерним элементом — занимаемая им
span-ячейка должна выглядеть целой.

# Задача

Подавлять сегменты перегородок под прямоугольниками детей — **общее
правило** (решение пользователя 2026-10-31, в противовес «строгому
выравниванию по ячейкам»):

- при рисовании перегородок в `_draw_grid()`/`drawGrid()` пропускать все
  клетки, попадающие в прямоугольник любого ребёнка (абсолютные
  координаты, half-open, clip по внутренней области grid);
- работает для любого выравнивания ребёнка: выровненный по границам
  ячеек → span выглядит целым; невыровненный → внутренность тоже чистая
  (под контентом нет линий);
- узлы `┼` под ребёнком тоже не рисуются; frame-узлы на внешней рамке
  (`┬┴├┤`) не затрагиваются (вне внутренней области, где живут дети);
- fill сохраняется под ребёнком (клетка перегородки просто не
  рисуется, fill/пробел под ней не трогается);
- HTML-оверлей не меняется (перегородок в нём нет — только ASCII-слой);
- `meta.col_span`/`row_span` не вводятся — span является следствием
  позиции/размера ребёнка; snap к ячейке — вариант 2 (follow-up,
  отдельная задача).

# Исследование

1. **Подавление на этапе рисования, не стирание.** Порядок: рамка →
   fill → перегородки → дети. «Стирать» перегородки постфактум нельзя —
   пробелом затирается fill. Правильно: до рисования перегородок
   вычислить прямоугольники детей (дети уже доступны:
   `block.children` / `allBlocks`) и пропускать покрытые клетки —
   fill/пробел под ними остаётся нетронутым.
2. **Прямоугольник ребёнка** — тот же оригин, что в
   `_render_children_in_container()`: `parent.x + 1 + c.x` (1-клеточный
   padding), clip по внутренней области (half-open). Активный clip не
   пересекается: клетки перегородок вне clip не рисуются `_set`/`setCell`
   в любом случае.
3. **JS: `drawGrid` не получает детей.** Блоки — плоский список
   (`allBlocks` + `parent_id`), дети ищутся в
   `renderChildrenInContainer`. В сигнатуру `drawGrid` добавить
   параметр `allBlocks`; место вызова одно (`renderBlock`).
4. **Границы.** Перегородка на границе ребёнка попадает в его
   прямоугольник (half-open) → подавляется. Следствие: между двумя
   соседними borderless-детьми перегородка исчезает. Для ребёнка с
   рамкой видимой разницы нет (рамка рисуется поверх).
5. **Производительность.** O(клетки перегородок × число детей) —
   пренебрежимо для MVP-размеров (grid 24×8, дети — единицы).
6. **Совместимость.** Вывод существующих макетов с детьми в grid
   меняется: перегородки под детьми исчезают. Это суть пожелания
   (замечание 3 задачи 0061 — «перегородка видна сквозь пустые клетки
   ребёнка» — заменяется этим правилом).
7. **Parity.** Логика тривиально портируется: целочисленные
   вычисления, прямоугольники, тот же split.

## Замечания

1. **E2E-тест: text-ребёнок не подходит.** `text` автосайзится (0049) —
   контент «SPAN» (4 символа) сжимает блок до 4×1, и он не дотягивает до
   перегородки. В e2e — `box` (без autosize) с явным размером 13×3.
   Прямой `render_simple` автосайз не применяет (берёт размер как есть),
   поэтому в unit-тестах `text` 13×3 работает.
2. **Parity.** Вывод Python и JS побайтово идентичен (parity-тесты).
