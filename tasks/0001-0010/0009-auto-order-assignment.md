# Суть проблемы

После внедрения z-order (задача 0008) обнаружилась проблема: старые блоки,
созданные до фичи, имеют `order=0` (дефолт из модели). При загрузке layout
все блоки с одинаковым order не имеют осмысленного порядка — `_reorderBlocks()`
сортирует их по insertion order, что не соответствует намерениям пользователя.

Также фронтенд вычисляет `MAX(order)+1` локально, но если сервер уже
перезагружен и новые блоки создаются без отправки order (например, через API
без явного order), они получают `order=0` и дублируют существующие.

# Задача

Обеспечить уникальные order для всех блоков на сервере:
- При создании блока без явного order — вычислять `MAX(order)+1` на сервере
- При загрузке layout — нормализовать order для старых блоков с одинаковым значением

# Исследование

Варианты решения проблемы одинаковых order:

1. **`created_at` как fallback** — блокам с одинаковым order присвоить sequential
   по времени создания. Выбрано для нормализации.
2. **UUID lexico order** — неочевидный порядок, не осмысленный.
3. **`INSERT`-order из БД** — зависит от id, может не совпадать с визуальным.
4. **`x + y` как fallback** — порядок зависит от координат, а не намерений.
5. **`0` и не трогать** — плохой UX при первом открытии.

Для `create_block` — сервер должен сам вычислять `MAX(order)+1`, чтобы не
зависеть от фронтенда. Это гарантирует уникальность order даже при прямом
API-вызове без order.

# Выполнение задачи

Изменены 2 файла:

**`services/layout_service.py`** (2 изменения):

1. `create_block()` — при `order=0` (default/unsent) вычисляет:
   ```python
   max_order = select(func.coalesce(func.max(Block.order), 0)).where(
       Block.layout_id == layout_id
   ).scalar() or 0
   order = max_order + 1
   ```
   Явный `order > 0` игнорируется — пользователь может задать любое значение.

2. `_normalize_block_orders(blocks)` — проверяет наличие **дубликатов** order.
   Если все order уникальны — не трогает (пользователь явно расставил).
   Если есть дубликаты — присваивает `min+0, min+1, min+2...` по `created_at`,
   сохраняя минимальное значение order.

3. `get_layout()` — вызывает `_normalize_block_orders()` после загрузки.
   Изменения не сохраняются в БД (mutable objects в ORM session), но
   фронтенд получает нормализованные order.

**`tests/api/test_layouts.py`** (5 новых тестов):

- `test_create_block_auto_order` — 3 блока без order → сервер назначает 1, 2, 3
- `test_create_block_explicit_order` — order=10 → следующий блок получает 11
- `test_normalize_block_orders_on_load` — все order=0 → нормализуются в 0, 1, 2
- `test_normalize_does_not_touch_unique_orders` — order 0 и 5 (уникальные) → не меняются
- `test_normalize_with_duplicates` — order [0, 0, 3] → нормализуются в 0, 1, 2

Все 62 теста прошли.

## Последующее изменение

**Commit `f38db86`** — нормализация теперь срабатывает при наличии **любых дубликатов**
order, а не только когда все order одинаковые. Это исправляет макеты типа "win", где
6 блоков имели order=1 и 1 блок order=0. Раньше нормализация не срабатывала (смешанные
order), теперь — срабатывает, так как есть дубликат order=1.

# Замечания

1. **Нормализация не сохраняется в БД** — `_normalize_block_orders()` меняет
   order на ORM-объектах в памяти, но не делает `commit()`. Это намеренно:
   нормализация — это view-логика для фронтенда, не нужно писать в БЗ.
   Но если другой код читает order из session, он увидит изменённые значения.

2. **order=0 → MAX+1** — это означает, что первый блок в layout получает
   order=1, а не order=0. Это не проблема (z-index = 10 + order), но
   стоит учитывать при чтении кода.

3. **API-клиенты без order** — если есть внешний API-клиент, который
   создаёт блоки без order, они автоматически получат MAX+1. Это корректно.

4. **Экспорт JSON** — `export_json()` всё ещё не включает `order`.
   Если order нормализуется только в памяти, экспортированный JSON
   будет содержать старые order-значения из БД.
