# Суть проблемы

В дереве элементов (задача 0081) кнопки ↑/↓ меняют z-порядок блока среди
siblings. Но у большинства макетов блоки созданы без явного `order` — API
присваивает дефолт `order = 0` (`BlockCreate`/`BatchBlockCreate` в
`api/layouts.py`). Когда у группы siblings одинаковый `order`, их реальный
z-порядок определяется tie-breaker'ом `_seq` (порядок вставки), а не значением
`order`.

`moveBlockOrder` свапировал **значения** `order` двух соседей. При равных
значениях (`0 ↔ 0`) свап — no-op: значения не меняются, `_seq` остаётся,
эффективный порядок не сдвигается. При этом `canMoveUp`/`canMoveDown`
разблокированы (проверяют только позицию в отсортированном списке, `idx > 0`).
Итог: кнопка кликабельна, но клик ничего не делает — блок «застрял» и его
нельзя переставить относительно соседа с тем же `order`.

# Задача

Сделать ↑/↓ в дереве работоспособными для siblings с одинаковым `order`:
перемещение должно реально менять z-порядок. Сохранить обратную совместимость —
эффективный вывод старых макетов не должен измениться.

# Исследование

Эффективный z-порядок в редакторе задаётся сортировкой (и в `_reorderBlocks`,
и в `treeBlocks`, и в `_siblingsOf`):

```js
(b.order - a.order) || ((b._seq || 0) - (a._seq || 0))
```

т.е. по убыванию `order`, при равенстве — по убыванию `_seq` (позже созданный —
выше). `_seq` — монотонный in-memory счётчик документного порядка (`_seqCounter`),
не хранится в БД и проставляется при загрузке/создании.

Ключевой вывод: менять местами значения `order` бессмысленно, когда они равны —
надо привести `order` к уникальным значениям, отражающим текущий эффективный
порядок, после чего свап двух соседей даёт осмысленный сдвиг.

Рассмотрены варианты:

- **A. Свап позиций в `this.blocks`** (двигать tie-breaker, не `order`).
  Минус: для web-режима порядок в БД = позиция → нужен `replaceState`, тяжелее
  двух `updateBlock`.
- **B. Глобальная нормализация** при загрузке/первом движении.
- **C. Assign-into-gap** — присвоить перемещаемому блоку `order±1`.
  Минус: раздувание значений, риск коллизии с соседями выше/ниже группы.
- **D. Гибрид (принят):** при обнаружении равных `order` — нормализовать
  **всю группу siblings** к уникальной последовательной нумерации, отражающей
  текущий эффективный порядок, затем обычный свап двух соседей.

Почему нормализуется вся группа, а не только коллидирующие: точечная
нормализация «только равных» требует подбирать значения строго в диапазоне
между соседями с другим `order`, а при нехватке места — каскадно сдвигать.
Сплошная нумерация `n-1 … 0` гарантирует уникальность, сохраняет эффективный
порядок (рендер не меняется) и срабатывает один раз на группу — дальше
перемещения идут по быстрому пути.

# Выполнение задачи

Реализовано полностью (`static/js/editor.js`).

**`moveBlockOrder(blockId, delta)`** — стал диспетчером: нашёл `sibs`
(отсортированы сверху вниз), индексы `idx`/`target`; если
`block.order === other.order` → `_normalizeAndSwap`, иначе → `_swapOrders`.

**`_normalizeAndSwap(sibs, idx, target)`:**
- Сохраняет старые `order` (`oldOrders`) для откатa.
- Нумерует всю группу: `sibs[i].order = sibs.length - 1 - i` (верхний —
  старший, нижний — 0). Относительный порядок не меняется.
- Свапирует значения `order` у `idx` и `target`.
- Формирует `updates` (только реально изменившиеся) и персистит: один
  `updateBlock` если запись одна, иначе `batchBlocks({ update })`.
- При ошибке — откат `sibs[i].order = oldOrders[i]`.

**`_swapOrders(block, other)`** — прежняя логика свапа двух значений +
два `updateBlock`, для разного `order` (быстрый путь).

Значения при нормализации (пример: `order=0` ×3, в дереве сверху вниз
`[A, B, C]`): `A.order = 2`, `B.order = 1`, `C.order = 0`. Относительный
z-порядок сохранён; коллизия устранена.

**e2e-тесты** (`tests/e2e/test_editor.py`):
- `test_move_order_same_order_blocks` — два бокса `TWO_BOXES` (оба `order=0`,
  B выше по `_seq`). ↑ на нижнем (2,2) → он становится первым в дереве;
  проверяется, что значения `order` из tooltip (`z#N`) стали уникальными и
  у поднятого больше.
- `test_move_order_same_order_move_down` — ↓ на верхнем (14,2) → он уходит
  под (2,2).

Тесты: 415 py (non-e2e) + 476 js + 115 e2e — все зелёные; 2 новых e2e прошли,
регресса нет.

# Замечания

- **Обратная совместимость соблюдена:** нормализация меняет **данные** (`order`
  в БД), но не **эффективный вывод** — относительный порядок siblings
  сохраняется, старые макеты рендерятся идентично. Меняются только макеты,
  к которым применили ↑/↓; нетронутые остаются как были.
- Нормализация «чинит» группу однократно: после первого движения у всех
  siblings уникальные `order`, дальнейшие свапы идут по `_swapOrders`
  (два `updateBlock`, без батча).
- `batchBlocks` выбран вместо N×`updateBlock` намеренно: меньше сетевых
  запросов при_web-режиме; undo/redo (history) корректно отрабатывает batch.
- Осталось ограничение по смыслу (не баг): z-порядок живёт на уровне siblings
  внутри одного родителя; перемещение между разными контейнерами — отдельная
  задача (drag-and-drop меняет `parent_id`).
- Если в будущем понадобится «перетащить блок на произвольную позицию в
  списке» (не соседом) — нормализация уже даёт уникальные значения, можно
  вставлять по индексу без коллизий.
