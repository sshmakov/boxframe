# Суть проблемы

При рендере псевдографики z-индекс (`order`) учитывался только для
root-блоков: в `PseudoGraphicRenderer.render()` (и JS-порте) root-блоки
сортировались по `order` — блок с бóльшим `order` рисовался поверх.

Но **дети внутри контейнеров** сортировались по позиции `(y, x)`, а не по
`order` — z-индекс внутри контейнера игнорировался:

- `boxframe/services/renderer.py`, `_render_children_in_container`:
  `sorted(parent.children, key=lambda c: (c.y, c.x))`;
- `boxframe/static/js/core/renderer.js`, `renderChildrenInContainer`:
  `.sort((a, b) => (a.y - b.y) || (a.x - b.x))`.

В результате блок с высоким `order` (вынесенный наверх через
`moveBlockOrder` / поле Order в панели свойств) проигрывал перекрыванию
у нижнего по z-индексу соседа, если тот стоял ниже/правее по координатам.
Проверено на живом примере: два text-ребёнка в одной позиции,
`order=10` (вставлен первым) и `order=0` — рендерился `LOWH` (низкий
по z-индексу перекрывал верхний).

HTML-превью z-индекс уже учитывало (`z-index: 10 + order`), поэтому
расхождение было видно: в оверлее порядок один, в ASCII-арте — другой.

# Задача

Сделать так, чтобы при рендере z-индекс учитывался **полностью**:
элементы, находящиеся сверху (бóльший `order`), отрисовываются поверх
нижележащих — и для root-блоков, и для детей контейнеров:

1. Python-рендерер: сортировка детей контейнера по `order`
   (стабильная — при равном `order` сохраняется порядок вставки,
   как и для root-блоков).
2. JS-рендерер: то же самое (порт должен давать идентичный вывод).
3. Тесты: Python unit + JS unit (зеркальные сценарии) +
   parity-тест перекрытия детей с разным z-индексом.

# Исследование

1. **Root-блоки уже были правы.** `render()` сортирует root-блоки по
   `order` (`sorted(blocks, key=lambda b: b.order)`), и это поведение
   покрыто тестами (`test_render_sorts_by_order`). Значит, правило
   «бóльший order — поверх» уже принято; нужно лишь распространить его
   на детей контейнеров.
2. **Почему была сортировка по `(y, x)`.** Она появилась в initial
   commit вместе с clip-механизмом контейнеров и не была осознанным
   решением о z-порядке — просто детерминированный порядок обхода.
   После введения `order` (z-индекс, `moveBlockOrder`, поле Order)
   она стала расхождением с правилом root-блоков.
3. **Стабильность сортировки.** И `sorted()` (Python), и
   `Array.prototype.sort` (JS, ES2019+) — стабильные: при равном
   `order` сохраняется исходный порядок списка. Для root-блоков это
   порядок вставки (покрыто `test_render_default_order_zero`), для
   детей — порядок, в котором дети лежат в `parent.children`
   (Python) / в плоском списке стора (JS).
4. **HTML-превью менять не нужно.** `z-index: 10 + order` уже ставится
   на каждый блок (и детей, и root), CSS сам решает порядок
   перекрывания. После фикса ASCII-арт и оверлей согласованы.
5. **Глубже первого уровня.** `_render_children_in_container`
   рекурсивен: внук рисуется через тот же путь, поэтому фикс
   автоматически покрывает любую глубину вложенности.

# Выполнение задачи

Изменено 2 файла кода + 3 файла тестов.

**`boxframe/services/renderer.py`:**
- `_render_children_in_container` — дети контейнера сортируются по
  `order` (было: по `(y, x)`). Комментарий указывает, что правило
  совпадает с root-блоками в `render()`.

**`boxframe/static/js/core/renderer.js`:**
- `renderChildrenInContainer` — сортировка детей
  `(a.order || 0) - (b.order || 0)` (было: `(a.y - b.y) || (a.x - b.x)`).
  `(order || 0)` — на случай отсутствия поля (совпадает с тем, как
  `order` обрабатывается в `render()` для root-блоков).

**`tests/test_renderer.py`** — 2 теста:
- `test_render_children_sorted_by_order` — два text-ребёнка в одной
  позиции: `order=10` вставлен первым, `order=0` вторым; после фикса
  `HIGH` перекрывает `LOW` (до фикса — `LOWH`);
- `test_render_children_order_beats_position` — два box-ребёнка с
  перекрытием, у верхнего по z-индексу **меньший** `y` (позиция
  противоречит z-порядку); проверяется ячейка перекрытия: левая рамка
  `HIGH` (`│`) выигрывает у левого верхнего угла `LOW` (`┌`) —
  если бы решала позиция, `LOW` (нарисованный последним по (y,x))
  оставил бы `┌`.

**`tests/js/test_renderer.js`** — 2 зеркальных теста (плоский список
с `parent_id`).

**`tests/test_js_renderer_parity.py`** — `test_parity_children_order_overlap`:
контейнер с 4 детьми — два перекрывающихся box (order 10/0, позиция
противоречит z-порядку) и два перекрывающихся text в одной позиции
(order 5/1); побайтовое сравнение вывода Python и JS.

# Замечания

1. **Поведение изменилось для макетов с перекрывающимися детьми.**
   Раньше при равной позиции/близких координатах верхним оказывался
   ребёнок с бóльшим `y`/`x`; теперь — с бóльшим `order`. Для макетов
   без перекрытий детей вывод не меняется (порядок отрисовки
   несуществен, если клетки не пересекаются).
2. **`_normalize_block_orders` в сервисе.** При дубликатах `order`
   (старые блоки с `order=0`) сервис перенумеровывает их по
   `created_at` — значит, в типичных макетах `order` уникален и
   порядок детей полностью определяется z-индексом.
3. **Формат псевдографики не менялся.** Изменён только порядок
   отрисовки; набор символов, clip-механизм и canvas-расчёт
   не тронуты.
