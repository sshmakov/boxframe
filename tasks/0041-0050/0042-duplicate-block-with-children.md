# Суть проблемы

Дублирование элемента в редакторе (`Ctrl+D` / кнопка Duplicate) копировало
только сами выбранные блоки, **без их потомков**:

- `duplicateBlock()` (`boxframe/static/js/editor.js`) строил `creates`
  через `sel.map(...)` — по одному `create` на выбранный блок,
  `parent_id` копировался как у оригинала;
- если был выбран контейнер (`box`/`grid`/`sidebar` с детьми) — создавалась
  **пустая** копия контейнера, дети оставались только в оригинале;
- рекурсии по потомкам не было, хотя хелпер `_subtreeIds()` (BFS по
  плоскому списку) уже существовал и использовался в каскадном удалении
  и drag&drop.

В результате дублирование контейнера теряло всё содержимое: пользователь
получал пустую рамку рядом с оригиналом, а вложенные блоки — нет.
Тесты не покрывали вложенное дублирование (только «листовые» блоки),
поэтому расхождение не проявлялось.

# Задача

Сделать так, чтобы при дублировании элемент копировался **вместе со всем
деревом потомков**:

1. Корень каждой копируемой поддерева получает смещение на одну ячейку
   (для root-блоков — с клампом в `0,0`), как и раньше.
2. Потомки сохраняют свои **относительные** координаты и пере-привязываются
   к копии своего родителя.
3. Выбранный блок, который сам является потомком другого выбранного, не
   копируется дважды (покрыт поддеревом предка).
4. Одна операция = один шаг undo/redo; работает и в web-, и в static-режиме.
5. Тесты: JS unit (чистая функция) + e2e (контейнер с детьми).

# Исследование

1. **Почему не batch create.** Батч-эндпоинт
   `POST /{layout_id}/blocks/batch` создаёт блоки в одном запросе, но
   `parent_id` в `create` должен указывать на **уже существующий** блок —
   сервис валидирует родителя (`_validate_reparent`), а id копий
   присваивает сервер. Ссылка на id, созданный в том же батче, не
   проходит: к моменту валидации блок ещё не закоммичен. Поэтому
   «один батч на всё дерево» не работает.
2. **`replaceState` — готовый механизм.** Полная замена набора блоков
   (`PUT /{layout_id}/blocks` / `replaceState` в local-сторах) **сохраняет
   client-сгенерированные id** (`replace_blocks`: `id=data.get("id") or
   uuid4()`). Это ровно то, что нужно: клиент сам генерирует id для всех
   копий, строит дерево с корректными `parent_id` и шлёт его одним
   снапшотом. Операция атомарна, один шаг undo/redo, работает в обоих
   режимах (fetch → `replaceBlocks`, local → `replaceState`).
3. **`_subtreeIds` уже есть, но не подходит напрямую.** Он возвращает
   только **id** поддерева. Для дублирования нужна карта
   «оригинал → копия» и смещение только корня, поэтому написана отдельная
   чистая функция `buildDuplicates` (BFS, родители раньше детей — карта
   готова к моменту обработки потомка).
4. **Смещение корня.** Корень копируемого дерева сдвигается на `+1`
   (для root-блоков — `Math.max(0, x+1)`, чтобы не уйти за левый/верхний
   край). Потомки **не** сдвигаются — у них относительные координаты, и
   сдвиг корня уже переносит всё дерево.
5. **Дедупликация выбора.** Если выбраны и родитель, и его потомок —
   потомок не должен копироваться отдельно (он уже внутри копии
   родителя). Корни копируемых деревьев = выбранные блоки, которые не
   являются потомком другого выбранного (проверка по цепочке
   `parent_id`).
6. **Тесты не покрывали вложенность.** `test_panel_duplicate_creates_block_copy`
   и `test_group_duplicate_copies_all_selected` — только плоские блоки;
   поэтому баг не проявлялся.

# Замечания

1. **`duplicateBlock` перешёл с batch create на `replaceState`.**
   Это изменение механизма записи, а не только логики копирования.
   `replaceState` шлёт **весь** набор блоков одним снапшотом — для
   макетов с большим числом блоков запрос тяжелее, чем точечный batch
   create. Для MVP-размера макетов это не критично, но при росте
   макетов стоит вернуться к вопросу (например, расширить batch-эндпоинт
   поддержкой «ссылок на id из того же батча» или отдельным
   `createSubtree`).
2. **Клиентские id сохраняются.** Копии получают `crypto.randomUUID`
   на клиенте, и `replace_blocks` их не перебивает. Это важно для
   undo/redo (идентичность блоков стабильна) и совпадает с тем, как
   работает импорт.
3. **Порядок `order` копий.** Все копии получают `order` выше текущего
   максимума (`baseOrder+1, +2, ...`), поэтому дерево копий рисуется
   поверх оригинала. Если нужно, чтобы копия встала «рядом» по z-порядку
   с оригиналом — это отдельная настройка, сейчас не требуется.
4. **Static-режим покрыт автоматически.** `buildDuplicates` чистая,
   `replaceState` есть у всех сторов (memory/local/fetch), поэтому
   дублирование с детьми работает и в `static/editor/index.html`
   без бэкенда. Отдельный e2e для static не добавлялся (логика общая),
   но unit-тесты `buildDuplicates` покрывают саму сборку дерева.
5. **`_subtreeIds` не переиспользован.** Написана отдельная
   `buildDuplicates`, потому что нужна карта «оригинал → копия» и
   смещение только корня — `_subtreeIds` возвращает лишь список id.
   Две BFS-функции рядом — допустимо, они решают разные задачи
   (один — id поддерева для каскадного удаления, другая — сборка копий).
