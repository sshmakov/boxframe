# Суть проблемы

`content` — «только имя» (аудит todo-0001, 2026-10-22): отрисовка
идентична `box` (общий путь `_draw_border()` + `_draw_content()`),
дефолт 20×3 с текстом `[content]`, характерной отрисовки и
семантических дефолтов нет. Входит в группу «только имя» вместе с
`header`/`footer`/`sidebar`.

Требования к `content` шли из двух источников, и они совместимы:

1. **Аудит todo-0001** — `content` как часть семантической группы
   должен получить «семантические дефолты» (размер/пропорции основной
   области).
2. **Дизайн-документ «Элементы boxframe.md»** (Obsidian,
   `Aa/Элементы boxframe.md`) — `content` как **плейсхолдер текста**,
   примитив тира 1 «любой текст»: строки «lorem», обрезанные по
   ширине, последняя строка короче — «как абзац».

Оба прочтения объединены в спецификации `todo-0004-content-design.md`
(2026-10-29): **роль** (плейсхолдер текста) определяет отрисовку,
**семантический дефолт** (40×10) — размер по умолчанию.

# Задача

Реализовать вариант 2 из `todo-0004-content-design.md`:

- пустой `content` → **детерминированный lorem-плейсхолдер** (word-wrap
  по внутренней ширине, заполнение высоты, последняя строка короче
  ~70% — «как абзац»);
- непустой контент → word-wrap как раньше (без изменений);
- `meta.fill` подавляет плейсхолдер (как подавляет hint);
- дефолт нового блока — **40×10**, content `''` (плейсхолдер виден);
- закрыть пункт todo-0001 по `content` (приоритет 2).

# Исследование

1. **`content` — общий путь в обоих рендерерах.** Веток для него нет ни
   в `_render_block()` (`services/renderer.py`), ни в `renderBlock()`
   (`core/renderer.js`): рамка + word-wrap + hint `[content]` + fill.
   Плейсхолдер встраивается в `_draw_content`/`drawContent` — в
   ветку «пустой контент», рядом с hint.
2. **Hint `[content]` заменяется плейсхолдером.** Сейчас hint рисуется
   при `not content and has_border and w >= 4 and not fill`. Для
   `content` (без fill) вместо hint рисуются lorem-строки; для других
   типов hint не тронут.
3. **Путь контента переиспользуется как есть.** Плейсхолдер — это
   строки, рисуемые тем же механизмом, что и реальный контент:
   `v_align_offset` + `h_align_offset` (0051, фаза 3) →
   `meta.text_align`/`vertical_align` работают для плейсхолдера
   бесплатно.
4. **Генерация на каждом рендере, а не хранение.** Плейсхолдер
   вычисляется из текущего размера внутренней области → при resize
   строки переносятся/добавляются/отбрасываются («live re-layout» из
   Obsidian-документа). В БД/макетах ничего не хранится — экспорт
   несёт lorem-строки как есть (AI-readable).
5. **Бэкенд не меняется.** Типоспецифичной логики для `content` в
   `LayoutService` нет (только `hline`/`vline` — толщина, `text` —
   точный fit 0049, `divider` — autosize-рост 0057) — autosize/fit для
   плейсхолдера не нужен (размер — сохранённый, контент — генеративный).
6. **HTML-оверлей не меняется.** Контент блоков в оверлее не
   дублируется (живёт в ASCII-слое) → HTML-правки не нужны; parity
   покрывает ASCII.
7. **Дефолт — только `_blockDefaults` (editor.js).** Единственный
   источник дефолтов в обоих режимах (web: `addBlock`/drag-drop → API;
   static: тот же код → LocalStorageStore). API-дефолт `width=20` в
   Pydantic-схемах — общий для всех типов и не трогается (прецеденты
   0057/0058).
8. **Совместимость.** Старые макеты: `content` с пустым контентом
   вместо hint `[content]` теперь показывает lorem-плейсхолдер —
   осознанное изменение вывода, данных не затрагивает. Макеты с
   непустым контентом не меняются.

# Выполнение задачи

## Python

- `services/renderer.py`:
  - `LOREM_PLACEHOLDER` — фиксированный lorem-источник (~245
    символов, стандартный «lorem ipsum dolor sit amet…consequat.»);
  - `placeholder_lines(w, h)` — `(LOREM + " ") * (h + 1)` (гарантия ≥ h
    строк при любой ширине) → `_wrap_text(text, w)[:h]` → последняя
    строка укорачивается до `max(3, w * 7 // 10)` (только при `h ≥ 2`
    и `w ≥ 4`) — короче, «как абзац»;
  - `_draw_content()`: ветка `block_type == "content" and not fill and
    content_w > 0 and content_h > 0` → строки плейсхолдера через путь
    контента (word-wrap + align); иначе — hint как раньше.

## JS (parity)

- `core/renderer.js`: `LOREM_PLACEHOLDER` + `placeholderLines(w, h)` —
  зеркало Python (parity побайтово); `drawContent` — та же ветка.
- `editor.js`: `_blockDefaults("content")` →
  `{ width: 40, height: 10, content: "" }`.

## Тесты

- `tests/test_renderer.py` — 9 ASCII-тестов: дефолтный размер 40×10

  нет плейсхолдера).
- `tests/js/test_renderer.js` — зеркала тех же 9 кейсов.

# Замечания

1. **Word-wrap не заполняет строки до полной ширины.** Перенос по
   словам (0051) оставляет «ступеньку» в конце строк — lorem-абзац
   выглядит естественно, но тесты не должны предполагать
   `len(line) == content_w` для всех строк (только для последних —
   гарантированное укорочение).
2. **Плейсхолдер — генеративный, не хранится.** При resize макета
   строки перегенерируются; undo/redo snapshot'ы (0051) хранят
   сохранённые блоки, а не ASCII → конфликтов нет.
3. **Открытые вопросы todo-0004 (не блокируют):** `…` при переполнении
   реального контента (сейчас строки просто обрезаются); штриховка
   `▒▒▒` как `meta`-опция (отклонена в пользу lorem — AI-readable);
   smart placement (вариант 3) — отдельная задача на всю семантическую
   группу.
4. **Согласованный набор дефолтов группы** (todo-0004, замечание 1):
   `header` 40×3, `footer` 40×3, `sidebar` 8×16, `content` 40×10 —
   согласовать при закрытии пунктов todo-0001 по header/footer/
   sidebar.
5. **Кросс-ссылки:** todo-0001 (аудит, приоритет 2, пункт `content`
   закрыт), todo-0004 (спецификация, план выполнен), Obsidian
   `Aa/Элементы boxframe.md` (роль «плейсхолдер текста»), 0049
   (`text` — однострочный autosize, не конкурент), 0051 (механизм
   word-wrap/align), 0057/0058 (прецеденты дефолтов в
   `_blockDefaults`).
